# ゲート定義と通過条件（spec-driven 用）

ゲート判定（SKILL.md Step 2〜6。G0〜G4）で使う。**各ゲートは「揃っていないものを可視化して先に進めない」ための関所**。通過条件は observable（誰が見ても判定が一致する形）で確認する。

## 5ゲートの全体像

| ゲート | 目的 | 主な成果物 | 最頻の違反 |
|---|---|---|---|
| G0 要件 | 何を作るかの合意 | 要求文・受け入れ基準・スコープ外 | 曖昧なまま実装に着手 |
| G1 仕様 | どこに何を書くかの確定 | 仕様文書の更新（ドキュメント先）・影響度評価・条件の組み合わせ表（分岐がある場合） | コードだけ変えて仕様を放置 |
| G2 計画 | 実装可能な単位への分解 | タスク分解・テスト計画 | 大きすぎる一括実装 |
| G3 実装 | 仕様に沿った実装 | コード + テスト | 仕様にない挙動の追加 |
| G4 検証 | 完了の証明 | 受け入れ基準チェック結果・乖離ゼロ確認 | 「動いたから完了」 |

## G0 要件: 通過条件

- [ ] 要求が1〜2文で言語化されている（Why / What）
- [ ] **受け入れ基準が 3〜5 個**、観測可能な形（実行して判定できる）で書かれている
- [ ] スコープ外（今回やらないこと）が明記されている
- [ ] 要求の曖昧点は次のいずれかの状態になっている（勝手に補完しない）: (a) 質問して解消済み (b)「前提」として明記 (c) **バッチ実行等で対話できない場合**、SD-n に質問を記録し、回答なしで安全に進められる範囲にスコープを限定済み

曖昧な要求（「いい感じに」「使いやすく」）は、**実装案ではなく質問リスト**を返すのが G0 の正しい出力。

## G1 仕様: 通過条件

- [ ] 変更が影響する仕様文書を判断マトリクスで特定した（→ spec-docs-map.md）
- [ ] **仕様文書を先に更新した**、または依頼範囲が G2 以前のため**更新案（差分）を提示した**〔この場合の状態は「提案通過」〕。文書が存在しない場合は変更が影響する文書のみ最小構成で新設（`${FF_DEV_TOOLKIT_ROOT}/docs-template/` の対応テンプレートを使用。frontmatter は組み込み済み）
- [ ] 影響度を LOW / MEDIUM / HIGH で評価し、HIGH なら関係者確認・ADR・移行計画の要否を判定した
- [ ] 仕様の更新内容が受け入れ基準と矛盾しない
- [ ] 処理が入力・環境・外部応答・読み取り結果・状態のどれかで分岐する場合、[条件の組み合わせ表](#条件の組み合わせ表分岐がある場合)を作り、各行を受け入れ基準かテストへ対応づけた。分岐が無い場合は「分岐なし」と進行表へ 1 行記録すれば満たす（表は作らない）

## 条件の組み合わせ表（分岐がある場合）

分岐する処理は、どの条件の組み合わせで何が起きるべきかを実装前に一覧にする。分岐の軸を実装後に 1 つずつ足すと、レビューが 1 巡ごとに 1 組み合わせずつ抜けを返し、修正と再レビューの往復が抜けの数だけ増える。

**対象**: 次のどれかを処理が意図して扱い分ける（値ごとに成功・停止・警告・再試行などを変える）もの。どれにも当たらなければ表を作らず、「分岐なし」の記録だけで先へ進む。軽量モードでも、当たる分岐があれば表は省略しない（行を畳んで短くしてよい）。

- 入力の形: 空・欠落・不正形式・表記ゆれ（大文字小文字、値の書き方の違い）
- 実行環境: OS、依存コマンドの有無、設定値、環境変数、検索パス上の並び順
- 外部呼び出しの結果: 成功・一時失敗・恒久失敗・取得不能・中断。どの呼び出し位置で起きたかも軸にする
- 読み取り結果: ある・ない・壊れている・読めない。どの対象を読んだかも軸にする
- 状態と同時操作: 保存済みの状態の種類（進行中・停止済み・取消直後・期限切れ）、画面や処理の段階、並行して起きる書き込みの種類

**作り方**:

1. 軸を列挙し、各軸が取りうる値を全部書く。「その他」にまとめない
2. 軸の組み合わせを行にし、各行に期待結果（成功・停止・警告・再試行など、観測できる形）を書く。同じ結果になる行は畳んでよいが、畳んだ理由を書く
3. 各行に ID を付け、受け入れ基準かテストケースへ対応づける。G2 の対応表でこの ID を参照する
4. 期限・切断対策・エラー変換のように経路全体へ掛ける保証は、それを掛ける対象（関数・文・トランザクション・外部呼び出し）を全部列挙し、その一覧を軸の 1 つにする

表は進行表の G1 の証拠として置く。値は全部書いたうえで、同じ結果になる行を畳んで短くする（畳まずに行数だけを削らない）。期待結果が決まらない行は推測で埋めず、行 ID と対にして SD-n として記録する。レビューやテストで表に無い組み合わせが見つかったら、そのセルだけを直さず G1 に戻って軸ごと表を直し、同じ軸の残りの行も同時に埋める。

## G2 計画: 通過条件

- [ ] 実装を検証可能な単位に分解した（1 単位 = 1 つの明確な出力。目安 1〜3 日、セッション内なら 5〜15 分粒度）
- [ ] 各単位に完了条件（テスト・確認方法）がある
- [ ] 分解した単位の合計が受け入れ基準を全部カバーしている（対応表で確認）。条件の組み合わせ表がある場合は、その全行もいずれかの単位の完了条件（テスト）に対応している。期待結果が未確定で SD-n にした行は、テストを作らず SD-n の ID へ対応づけて未解決として残す（期待結果を推測で埋めない）
- [ ] 触ってよい範囲・触らない範囲（ファイル・モジュール）を明示した

## G3 実装: 通過条件

- [ ] 実装の根拠にした読み取りは**分岐後**に行ったものである（分岐前の読み取りに依存する一括置換をしていない）

- [ ] 実装は G1 の仕様を参照して行った（仕様にない挙動を足していない。必要になったら G1 に戻って仕様を先に更新。条件の組み合わせ表に無い分岐が要るときも、表を先に直してから実装する）
- [ ] 各単位のテストが存在し、パスしている
- [ ] 既存テストが壊れていない
- [ ] スコープ外に踏み出していない（踏み出しが必要なら G0 に戻すか別タスク化）

## G4 検証: 通過条件

- [ ] **受け入れ基準を1つずつ実行して判定した**（チェック結果を記録。未達があれば完了と言わない）
- [ ] 仕様文書と実装の乖離がない（変更が仕様に反映済みか最終確認）
- [ ] 影響度 MEDIUM 以上の場合、関連文書（テスト・運用）も更新した
- [ ] 学び（ハマりどころ・判断）があれば記録した（ナレッジ蓄積へ）

## ゲート運用の原則

- **飛ばさない・戻ってよい**: ゲートは順に通る。ただし後段で前提が崩れたら前のゲートに戻るのは正常（戻った事実と理由を進行表に記録する）
- **通過条件は自己申告にしない**: チェック項目は「実行した証拠」（質問と回答・更新した文書のパス・テスト結果）とセットで記録する
- **止まる勇気**: 通過条件が満たせないとき、無理に進めず「何が足りないか」を報告して指示を仰ぐのが正しい挙動
- 軽量モード（SKILL.md Step 1 の tier 判定が `light`。自己申告では決めない）では G1〜G2 を簡略化してよい（省略ではなく簡略化。受け入れ基準1個と影響度 LOW の確認は必須）
