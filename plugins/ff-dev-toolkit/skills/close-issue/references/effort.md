# 工数実績の書き戻し（`ff-effort` ブロック）と乖離帯の較正

`/close-issue` 手順 5a・6 の詳細。本線は「ブロックがあれば実績を書き戻し、帯の外なら乖離の原因を書く」だけを持ち、規則の全文はここに置く。閉じる Issue に `ff-effort` ブロックが無い回は読まなくてよい。

## 書き戻す値

- **AI 実績は観測事実つきで申告する**。人時換算そのものは AI の判断だが、根拠となる観測可能な事実（`gh pr view "$PR_NUMBER" --json additions,deletions,commits,reviews` の差分行数・コミット数・レビュー往復回数・品質ゲートの実行回数）を必ず併記する。事実を伴わない数字は報告として不完全に扱う — 検証できない数字は KPI の母集団を汚す
- **単位はブロックの宣言に従う**。`- effort_unit: h` 行のあるブロックは `N.Nh`（小数第 1 位まで、最小 1.0h。bundle の内訳は下の例外に従う）、宣言の無い旧ブロックは起票時と同じ `N.Nd`（1d = 8h）で書く。宣言と食い違う単位で書くと集計器が `excluded_unit_mismatch` として母集団から外す
- **hook の実測を自己申告値と並記する**（`effort_ai_actual` を置き換えない）。値は `finish.sh precheck` の `EFFORT_<Issue番号>_*` 行（`scripts/effort-report.sh --issue-metrics <Issue番号>` の読み出し。記録は `${FF_DEV_TOOLKIT_STATE_DIR:-$HOME/.config/ff-dev-toolkit}/metrics/` から作業中のリポジトリの行だけを読む）: `wallclock_actual_h` を `effort_wallclock_actual: N.Nh`（ブランチ作成からこの書き戻し時点 = マージ直前まで）、`instruction_bytes` を `effort_instruction_bytes: N`、`review_rounds` を `effort_review_rounds: N`（レビュー巡回カウンタの記録から、その Issue のブランチで起動したレビューの異なる HEAD の個数 = 巡）、`gate_minutes` を `effort_gate_minutes: N`（`tests/run-all.sh` が終了時に記録したうち、正規ゲート起動 `mode=fast` / `full` / `changed` の所要秒だけを合算して分にしたもの。`mode=explicit` 等の明示引数実行は合算しない。回数は `gate_runs`）、`change_class` を `effort_change_class:`（`docs-only` / `small` / `other`）として書く。記録置き場が無い・読めない・hook を `FF_DEV_TOOLKIT_SKIP=effort-metrics` で止めている等で値が `(unmeasured)` のときは、そのまま `(unmeasured)` と書く（0 と書かない・マージは止めない）。この 5 行は Issue 単位の累積値なので、1 Issue に複数 PR でも加算せず最新の値で置き換える
- **人間の実績は書かない**（`effort_human_actual` という項目は作らない）。人間は実際には作業しないため実績は原理的に取れず、人間側は永久に予定（反実仮想）である
- **乖離率はブロックに書かない**。`effort_ai_planned`（加算予定行があればその合計を足した値）と `effort_ai_actual` から導出できる値であり、下の「1 Issue に複数 PR」の実績の加算で静かに stale になる。乖離率は完了報告コメントと集計器がその都度計算する（加算予定は下の「[加算予定](#加算予定effort_ai_planned_added)」）

MCP: 取得値: MCP で同じ PR の additions / deletions / 全 commits / reviews を取得。形式: 各実値を保つ JSON と実行済み gate / review の記録。渡し先: 工数実績の観測事実と effort_evidence へ渡す（この段で merge はしない）。不足時: MCP 必須 field 不足は未確認と記し、根拠を取れるまで実績の算定を停止する。

- **サブエージェントを使った回の観測事実に `task-notification` の `duration_ms` を加える**。並行・直列を問わずサブエージェントを使った回は、hook の wall-clock だけでは担当ごとの作業時間が分からない（hook の実測が `(unmeasured)` の回を含む）。ホストの完了通知（`task-notification`）に含まれる `duration_ms` を完了済みの担当ごとに足して `effort_evidence` に並べ、統括の分を「約」として分けて書く。**API の上限・エラー・中断などで途中で止まった回の通知は数えない**
- **起票後に範囲が広がった Issue の書き戻し**: 起票後に利用者の依頼で作業が追加された場合は、`effort_ai_actual` に何を含めたか（起票時の範囲だけか、追加分も含むか）と追加分の内訳（追加分を含めた場合は後から差し引けるよう追加分の所要目安 `h` も記す）を `effort_evidence` に書く（記事・コンテンツ系の補正元として後から比べるとき、追加分を除けるようにする）。追加の時点で加算予定行を足していれば、その行が追加分の予定になる。範囲が縮んだときもここに書く（加算予定行を負の値で書いて引かない）
- **補正元で見積もった Issue の書き戻し**: `effort_basis` に補正元の Issue 番号がある Issue（補正元の実績比で見積もった Issue。比を減じた Issue を含む）では、帯の内外にかかわらず、`effort_evidence` に実績の内訳（実装分とレビュー対応分）と、着手後の範囲の変化の有無（加算予定行の有無・範囲が縮んだこと）を書く。内訳が無いと、減じた見積もりが帯の内側に入ったとき、比を減じた判断が当たったのか、レビュー対応分の見込み過大と相殺したのか、範囲が縮んだのかを後から読み分けられず、同じ減じ方を次も使うかを決められない（導入先の観測台帳で、帯の内側に入った 3 件のうち内訳を残した 1 件だけが「相殺」と読めた）

按分・加算の規則:

| 状況 | 扱い |
| ---- | ---- |
| 1 PR が複数 Issue を閉じる（bundle 以外） | 各 Issue の `effort_ai_planned` **比で按分**する。等分は大小混在で嘘になる。明らかに比と違うと判断した場合のみ上書きし、按分根拠を `effort_evidence` に 1 行書く |
| 1 Issue に複数 PR | `effort_ai_actual` が記入済みなら**加算**する（上書きしない）。加算した旨を `effort_evidence` に書く |

### bundle と子を 1 PR で閉じる場合

上表の一括按分より、この規則を優先する。まず PR 全体の実績を、共通の固定費と子ごとの実装分（指摘の修正・偽陽性潰しを含む）に分け、差分量・レビュー往復数・ゲート回数の観測を根拠にする。

- **実装分だけを子の見積もり比で配り、固定費は束ね全体で 1 回分として扱う**。固定費の範囲は [推定手順](../../create-issue/references/estimation.md#bundle-の固定費と子の内訳) と同じ。子の予定が単独 PR 前提なら、元の値を保存したまま bundle 本文の実装分の比を使う。分離できない予定値をそのまま比として使わない。
- **親には固定費だけ、子には配分した実装分だけを書き戻す**。親に全体実績を置いて子の実績を再計上しない。親にも子にも、ブロック不在なら新設せず、完了報告へその記録対象外の内訳を残す。既存の予定値・`effort_basis` は変更しない。ただし、bundle 本文の加算予定行（起票後に bundle へ足した範囲）に対応する実装分は、子へ配らず親へ書き戻す（加算予定を置いた Issue と実績を置く Issue をそろえる。子へ配ると、親は過大側・子は過小側へ同時に外れる）。
- **ブランチと別の番号の Issue には実測を複写しない**。hook の実測はブランチの Issue 番号をキーに PR 全体で 1 本だけ記録される。自分の実測が無い Issue（bundle の子など）には `EFFORT_<Issue番号>_measured_on=<番号>` が出るので、4 指標の行を書かず `effort_measured_on: #<番号>` と `effort_change_class:` を書く。集計器は 4 指標の行が無い Issue を未計測に数えない。自分のブランチの実測が残っている Issue はこの行が出ず、通常どおり実測を書く。
- **ブロックを持つ子が 1 件だけ、または全子の実装分の比を確定できない場合は、編集面・作業記録など何の比で配ったかを `effort_evidence` に書く**。唯一の記録対象へ全子の実装分を押し込まず、ブロックを持たない子の分も全体実績との照合に含める。
- **`effort_evidence` に固定費・実装分・按分比・記録先を併記し、完了報告で「記録した合計 + ブロック不在分 + 丸め差 = PR 全体実績」を照合する**。bundle の内訳には最小 1.0h の個別切り上げを適用せず、正の値を宣言単位の小数第 1 位で記録する。丸め差は完了報告に別記し、親の固定費へ押し込まない。旧 d ブロックとの混在時は 1d = 8h で換算して照合する。親のブロックが無い場合も同じ扱いとする。丸めで 0 になる配分は数値を捏造せず、配分を確定できない旨と未丸め値を完了報告に残す。
- 旧予定が単独 PR 前提で帯外になった場合、乖離の原因欄に **「束ねたことによる固定費の畳み込み」** と、共通化した作業を明記する。元の予定を下げて乖離を隠さない。1 Issue に複数 PR の加算規則は維持し、今回分の内訳を既存実績へ加える。

例: 全体実績 4.0h = 固定費 1.0h + 実装分 3.0h、子 A:B の実装予定比が 1:2 なら親 1.0h・A 1.0h・B 2.0h。B にブロックが無ければ記録値合計 2.0h + 記録対象外 B 2.0h = 4.0h と報告する。子 A だけにブロックがあり比も不明なら、編集面等から配分を判断し、その根拠を A の `effort_evidence` へ残す。

例えば固定費 1.0h を旧 d ブロックへ 0.1d と記録し、子の実装分が 3.0h なら、記録値 3.8h + 丸め差 0.2h = 全体 4.0h と報告する。

書き戻す形（`effort_basis` は起票時のまま保持し、`effort_evidence` を足す）:

```markdown
<!-- ff-effort:begin -->
- effort_unit: h
- effort_human_planned: 24.0h
- effort_ai_planned: 4.8h
- effort_deploy: なし（コードのみ・反映を伴わない）
- effort_ai_actual: 11.2h
- effort_wallclock_actual: 6.5h
- effort_instruction_bytes: 431000
- effort_review_rounds: 2
- effort_gate_minutes: 47
- effort_change_class: other
- effort_evidence: diff +412/-88 / レビュー往復 2 / fix commit 2 / 全件ゲート 3 回
- effort_basis: （起票時のまま）
<!-- ff-effort:end -->
```

マーカー行 `<!-- ff-effort:begin -->` / `<!-- ff-effort:end -->` は**綴りを変えない**。集計器 `effort-report.sh` がこの 2 行を境界に本文を切り出すため、変えると集計から静かに落ちる。

## 加算予定（`effort_ai_planned_added`）

起票後に AC・作業・部分 PR が足された Issue では、起票時の `effort_ai_planned` と `effort_basis` を書き換えず、足した分の予定を加算予定行として工数ブロックへ 1 行足す。書式は次の 1 通りで、`/create-issue` の [estimation.md「起票後に範囲を足すときの加算予定」](../../create-issue/references/estimation.md#起票後に範囲を足すときの加算予定) と同じである（足す時機と見積もり方の正本はあちら）:

```markdown
- effort_ai_planned_added: +N.Nh（YYYY-MM-DD <経路と件数>。<根拠 1 行>）
```

- 範囲を足すたびに 1 行足し、既存の行の値を書き換えない。集計器はこのキーだけ複数行を合計する（予定・実績・単位の 4 キーの重複は書式不正のまま）。値はブロックの単位宣言に従い（宣言の無い旧ブロックは `+N.Nd`）、正の値を小数第 1 位まで書く。1 行に書く値は 1 つで、2 つ目の値や幅を続けない（集計器は読めない行として扱う）
- 足す先は、AC・作業を足した Issue の工数ブロックとする。bundle では、子にブロックがあり子の AC・作業が増えたなら子のブロックへ、そうでなければ bundle 本文のブロックへ足す。bundle 本文へ足した分の実装の実績は、上の bundle の節のとおり親へ書き戻す（分子と分母を別の Issue に分けない）
- **乖離率は `実績 ÷ (予定 + 加算予定の合計)` で出す**。完了報告の工数実績の表では、予定欄を `4.5h + 加算 3.0h` のように分けて書き、備考に `乖離率 1.73（13.0 ÷ 7.5）` のように式を添える。圧縮率は起票時の人間予定のままで、加算予定は乖離率の分母にだけ入る
- **今回の PR で実装した追加分の加算予定行を、マージ直前に後から書き足さない**。実績を見てから予定を足すと、乖離率が見積もりの当否を測らなくなる。加算予定行が無いまま起票後に AC・作業が足されていた Issue（本文の追記・コメントでの追記・部分 PR の追加）は、乖離率を起票時の予定のまま出し、帯の外なら乖離の原因に「起票後に足された範囲の予定が無い」と、追記の日付と件数を添えて書く。ただし、その分の実装より前の日付のコメントに `追記分の予定（目安）` が書かれていて、本文へ写し忘れていただけなら、その値を変えずに写してよい（値は実績を見る前に決まっている。根拠に目安を書いたコメントの日付を残す）
- Refs 運用で Issue を open のまま残し、残りの AC・作業を後続の PR へ回すときは、起票時の予定に含まれていない後続分（起票後に足した AC・作業の実装分 + レビュー対応分と、PR を分けて増える固定費）だけを加算予定行で足す。起票時の AC の残りは予定に入っているので足さない（足すと分母が二重になり、過小見積もりが帯の内側に隠れる）。スコープ変更を伴わないときは、手順 5b の 1 回目の送信（`ff-effort` の書き戻しと同じ送信。判定器はブロックの中の行の追加を許す）に含める。手順 4 のスコープ変更で AC を足すときは、AC 行を足す 2 回目の送信が通った後に、工数ブロックだけを変える送信（判定器を通す）で足す。2 回目を止めたときに、存在しない AC の予定行を本文に残さないためである。後続分はまだ実装していないので後付けに当たらない。open のまま残す回の乖離率は途中経過で、閉じる PR の完了報告で確定する
- 読めない行（`+` が無い・正でない値・単位の食い違い・値や注記の後ろに別の値や文字が続く・閉じていない注記・字下げや全角コロンや `*` / `+` の箇条やブロックの外に書いた加算行）がある Issue は、足した予定が分からないので、集計器が乖離率の母集団から外して `variance_excluded_added_unreadable_issues` に番号を出す（0 として足さない。実績の合計と圧縮率には残り、`ai_planned_total` からは外れる）。名指しされるのは、実績が記入済みで `effort_ai_planned` が正の Issue だけなので、着手時に書いた行の誤りは閉じて集計するまで見えない。名指しされた行は、値を変えずに書式だけを直してよい（値を変えるのは後付けに当たる）。値が読み取れない行（空・数値でない・0）は直す値が無いので、行ごと消す（加算なしとして扱われる。足すつもりだった値を後から決めて書かない）。ブロックの外のコードフェンスの中の書式の例・キーで始まるだけの散文・行全体を inline code で引いた箇条は名指ししない

## 配備の行（`effort_deploy`）の照合

`effort_deploy` は `/create-issue` が必須項目として書かせる配備の行である（誰がどこで反映し、成否を誰がどう確認するか。反映を伴わない変更は `なし（コードのみ・反映を伴わない）`）。この照合は手順 5a の中で行い、排他的に確保した私有領域へ本文を取得する。変換後の W の実値を記録し、5b・6 の新しい Bash 呼び出しでもその同じ実値を明示して再設定する。固定名から再構築せず、後続段で mktemp を再実行しない。5b は同じパスへ本文を取り直してから編集する。照合が不要だった場合は 5b の初回に私有領域を確保する。任意の照合なので確保・変換失敗は `effort_deploy=unavailable` として続ける。置き場所と寿命の正本は [Markdown 文字列パッチ規律の「一時ファイルの置き場所」](../../../docs-template/05-operations/deployment/markdown-patch-discipline.md#一時ファイルの置き場所)。

```bash
if ! W="$(mktemp -d "${TMPDIR:-/tmp}/close-issue-${ISSUE_NUMBER:?Issue 番号を先に設定すること}.XXXXXX")"; then echo "effort_deploy=unavailable"; exit 0; fi
[ -d "$W" ] && [ ! -L "$W" ] || { echo "effort_deploy=unavailable"; exit 0; }
if command -v cygpath >/dev/null 2>&1; then W="$(cygpath -m "$W")" || { echo "effort_deploy=unavailable"; exit 0; }; fi
echo "W=$W" >&2  # この実値を記録し、後続呼び出しの W に明示する
BODY_ORIG="$W/issue-body-${ISSUE_NUMBER}.orig.md"
# 取得に成功したときだけ確定する（失敗時にリダイレクトが残す空ファイルを「ブロック不在」と読ませない）
if gh issue view "$ISSUE_URL" --json body --jq .body > "${BODY_ORIG}.part"; then
  mv "${BODY_ORIG}.part" "$BODY_ORIG"
  FF_DEV_TOOLKIT_ROOT="${FF_DEV_TOOLKIT_ROOT}" bash "${FF_DEV_TOOLKIT_ROOT}/scripts/effort-report.sh" --deploy-check "$BODY_ORIG"
else
  rm -f "${BODY_ORIG}.part"
  echo "effort_deploy=unavailable"
fi
```

MCP: 取得値: MCP で同じ Issue の body 全文を取得。形式: 成功時だけ本文原文を BODY_ORIG（.orig.md）へ保存。渡し先: effort-report.sh --deploy-check "$BODY_ORIG" へ本文ファイルを渡す。不足時: 任意の本文取得失敗は effort_deploy=unavailable と報告して継続し、未取得を空ファイルやブロック不在にしない。

- 出力は `effort_deploy=<状態>` の 1 行で、常に exit 0。`present`（「なし（…）」の明示を含む）と `noblock`（ブロック不在。5a のスキップと同じ）は何もしない
- **`missing`（キーが無い）・`unfilled`（空・全角空白だけ・`(未記入)` / `（未記入）`・雛形の `[ … ]` のまま）・`malformed`（未閉鎖・end だけ・2 組目のブロック・余分な end・キーの重複）・`unavailable`（本文を取得できない・読めない）なら、完了報告の工数実績セクションへ「配備の行が未記入（`effort_deploy=<状態>`）」の 1 行で指摘する**
- **マージは止めない**。既存 Issue への遡及付与は強制せず、ブロック内の配備の行を後から書き足させることもしない（書くのは起票者の見積もりで、実績の書き戻し側が推測で埋めない）
- 集計器の本体はこのキーを読まない。記入の有無で乖離率・圧縮率の母集団は変わらない

## 完了報告コメントの工数実績セクション

```markdown
### 工数実績

| 区分 | 予定 | 実績 | 備考 |
| ---- | ---- | ---- | ---- |
| 人間（換算） | 24.0h | — | 実作業なし。圧縮率の基準線 |
| AI | 4.8h | 11.2h | 乖離率 2.33（閾値 2.00 超） |

観測事実: diff +412/-88 / レビュー往復 2 / fix commit 2 / 全件ゲート 3 回
配備の行: `effort_deploy=present`（未記入なら「配備の行が未記入（`effort_deploy=missing`）」）
圧縮率: 24.0h ÷ 11.2h = 2.1 倍

**乖離の原因**: 契約ゲートの mutation テストが予定に入っていなかった（レビューで要求され 4.0h 相当を追加）
```

- 加算予定行がある Issue は、予定欄と備考を上の「[加算予定](#加算予定effort_ai_planned_added)」のとおり分けて書く（例: 予定 `4.5h + 加算 3.0h`・実績 `13.0h`・備考 `乖離率 1.73（13.0 ÷ 7.5）`）
- **`ff-effort` ブロックが無い Issue では節ごと省略する**（手順 5a のスキップと対になる）
- 人間の実績欄は常に `—`。「まだ埋めていない」ではなく「原理的に埋まらない」の意味である
- **乖離率が閾値の外（`0.50` 未満 または `2.00` 超）にある場合、「乖離の原因」は必須**。何が予定に無かったか（過小）／何を過剰に見込んだか（過大）を書く。閾値内なら省略してよい。**端ちょうど（`0.50` / `2.00`）は帯内**である
- **帯の外と 2 倍超は役割が違う**: 帯の外（`0.50` 未満 または `2.00` 超）は「乖離の原因」の記録を必須にする線、2 倍超（乖離率 `2.00` 超。2026-09-30 の較正では上限と一致）は原因の記録に加えて見積もりの前提（スコープの切り方・推定手順）そのものを見直す線である。上限が 2 倍の線と重なるのは 2026-09-30 の較正で `1/p25` が上限を決めた結果で、次の較正で上限が動いても「2 倍超は前提の見直し」の線は動かさない
- **`0.50` は `1/2.00` であり、帯は乗法的に対称である**（どちらの方向にも 2 倍）。加法的な ±100%（= 下限 `0.00`）ではない。この導出を書かないと、「対称性を直す」つもりで加法側へ置換されたときに**すべてのゲートが緑のまま**過大側の検出帯が広がる（検査は 3 箇所の一致しか見ない）
- **この 2 値の複製先は 3 箇所**: 本ファイル（正本）・`/retrospective` の記録帯（`skills/retrospective/references/effort.md`）・`scripts/effort-report.sh` の `VARIANCE_LOWER` / `VARIANCE_UPPER`。変えるときは 3 箇所すべてを同時に直すこと
- 観測事実は手順 5a で取得した値をそのまま書く（記憶から書かない）

## 帯の較正手順（実測分布から引く）

閾値 `0.50` / `2.00` は**実測分布から導出した値**である。出荷時の暫定値（`0.77` / `1.30`。「0.6d 予定に対し 0.75d は運用上の誤差だが 2 倍は前提が壊れている」という設計判断）を 2026-09-10 に 3 リポジトリ・母集団 78 件で `0.71` / `1.40` へ較正し、2026-09-30 に 5 リポジトリ・母集団 234 件で現在の値へ引き直した。帯は導入先ごとに引かず、複数の導入先の合算で引く（共通帯）。次に較正するときも同じ手順で引く:

1. **母集団を取る**。`scripts/effort-report.sh --repo <owner/repo> --format kv` の `variance_population` が較正母集団で、その条件は集計器の除外規則と同一である — `effort_ai_actual` と `effort_ai_planned` がブロックの単位宣言どおりの正の数で記入されていること（`effort_unit: h` なら `N.Nh`、宣言の無い旧ブロックは `N.Nd` を 1d = 8h で人時へ正規化。乖離率は比なので単位に依らない）。加算予定行のある Issue の乖離率は予定 + 加算予定の合計で出る。次のものは母集団に入らない: `ff-effort` ブロック不在（`excluded_noblock`）／実績が未記入（`excluded_planned_only`）／**実績が複数 PR の加算更新の途中にあり同じキーが 2 行ある**・数値でない値・未知の単位宣言・未閉鎖ブロック（いずれも `excluded_malformed`）／単位宣言と値の単位の食い違い（`excluded_unit_mismatch`）／加算予定行に読めない行がある（`variance_excluded_added_unreadable`。乖離率の母集団からだけ外れる）。`suspect_marker` が 1 以上・`limit_reached=1` のまま較正しない（前者は本文が読めていない Issue が落ちている、後者は母集団が打ち切られている）
2. **分位点を読む**。同じ出力の `variance_p10` / `variance_p25` / `variance_median` / `variance_p75` / `variance_p90`。`variance_median_position` が `in_band` でなければ 3 以降へ進まない（中心がずれた分布は帯を引き直さず推定手順側を直す。分岐の正本は `/retrospective` の references/effort.md）
3. **上限を引く**。`上限 = max(p75, 1/p25)` を小数第 2 位へ丸める。これで帯は「中央値を中心に p25〜p75 を包む乗法対称帯」になる
4. **下限は上限の逆数**。`下限 = 1/上限` を小数第 2 位へ丸める。**乗法対称を崩さない**（加法的な ±x% にしない）
5. **p10〜p90 を包む案は採らない**。実測では下側の裾が長く（234 件で p10 = 0.30）、p10 を包むと上限が 3.3 倍まで広がって「2 倍は前提が壊れている」という判定機能が消える。下側の裾は帯を広げて隠す対象ではなく、`/create-issue` の目安表・推定手順で詰める対象である
6. **3 箇所を同時に直し**、`tests/effort-contract` の閾値検査と帯の端の fixture（`fixtures/band-edge.json`）も新しい値へ合わせる

較正に使った分布（2026-09-30・5 リポジトリ合算 234 件）: p10 = 0.30 / p25 = 0.50 / 中央値 = 1.00 / p75 = 1.38 / p90 = 2.00。上限 = max(1.38, 1/0.50 = 2.00) = 2.00、下限 = 1/2.00 = 0.50。前回（2026-09-10・3 リポジトリ合算 78 件）は p25 = 0.75 / p75 = 1.40 から上限 = max(1.40, 1.33) = 1.40、下限 = 0.71 を引いていた。導入先別の内訳は `/retrospective` の references/effort.md にある。
