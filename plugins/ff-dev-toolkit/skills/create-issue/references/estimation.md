# 工数の推定（/create-issue）

`/create-issue` の SKILL.md 手順 3「工数の推定（KPI 計測）」で工数ブロックを書くときに読む（毎回）。単位・非対話モードでの扱い・ブロックの契約は SKILL.md が正本で、ここには過去実績の引き方・目安の値・積み方だけを置く。本文中の「手順 N」は SKILL.md の手順を指す。

## 過去実績の参照（3 層すべて）

過去の予実を **3 層すべて**から引く。1 つでも欠けると「記録するだけで参照されない層」ができる。

| 層 | 参照先 | 引き方 |
| ---- | ------ | ------ |
| 知見 | ACE Playbook の `estimation` カテゴリ | `PLAYBOOK.md` の索引テーブルを**カテゴリ列 `estimation` で絞って**引く。手順 2 の対象領域の検索とは別枠（キーワード一致では見積もり知見は偶然一致したときしか出ない） |
| パターン | `docs/08-knowledge/OBSERVATIONS.md` | 見積もり語彙（工数・見積もり・乖離・過小・過大）で検索し、`Kind: problem` と `Kind: keep` の**両方**を見る |
| データ | closed Issue の工数ブロック | `gh issue list --repo "$expected_repo" --state closed --search "<類似領域のキーワード>" --limit 30 --json number,title,body` を実行し、`ff-effort` ブロックを読む |

`Kind: keep`（当たった見積もり方）を無視して `problem`（外した例）だけを見ると、補正が「バッファを積む」方向へ一方向に偏り、系統的な過大見積もりになる。

引いた結果は、**見つからなかった経路も含めて** `effort_basis` に残す。参照先が存在しないプロジェクトでは、その経路を「参照先なし」として扱い、見積もりは続行する。

## 人間工数の目安

**2026-09-10 に 3 リポジトリ・母集団 78 件で較正済み**（較正は人日で行い、表の値は 1d = 8h で人時へ換算したもの）。人間工数の実績は原理的に取れないので、行の値を直接反証するデータは無い。再較正の発火条件と手順は `/retrospective` の [references/effort.md](../../retrospective/references/effort.md)「集計レポートの実行（較正トリガの唯一の発火点）」が正本。

| 規模の目安 | 人間工数 |
| ---------- | -------- |
| 1 行の文言・リンク修正（ゲート 1 周で終わる） | 2.4h |
| 1 ファイル・数行の修正、文言変更 | 4.0h |
| 1 機能の追加（既存パターン踏襲、テスト込み） | 8〜24h |
| 新規スキル / モジュール 1 本 + ゲート + テスト | 24〜40h |
| 複数コンポーネント横断、設計判断を含む | 40〜80h |
| それ以上 | Issue を分割する（SKILL.md 手順 4「単一責務か」） |

**行は「設計判断を含むか」の語感ではなく、変更の物量で選ぶ**（触るファイル数・新規ファイルの有無・ゲート追加の有無）。較正母集団では、人間予定の中央値が 8h（30 件）から 32h（16 件）へ 4 倍になっても、AI 実績の中央値は 4.4h → 4.0h でほぼ動かなかった。動いたのは AI 予定（3.2h → 10.0h）で、上位行を選んだ Issue ほど AI 工数が人間工数に引きずられて置かれていた。

## AI 工数の目安

AI 工数は「人間工数 ÷ 圧縮率」で導出しない（除算で導くと圧縮率が定数になり、KPI が何も測らなくなる）。レビュー往復・品質ゲートの実行・fix commit を織り込んで、次の実測値から独立に積む。

| 変更の種類 | AI 工数 | 出所 |
| ---------- | ------- | ---- |
| 1h 未満で済む小変更（1 行の文言・設定値・リンク） | **1.0h**（検証 2 回分を含む。これが最小値） | 較正母集団で AI 予定 1.2h 以下の 9 件は**全件が乖離率 1.00 以上**（最大 1.67）で、下振れが 1 件も無い。それより下へは置かない |
| View・画面の変更 | 2.0h（クロスモデルレビュー 2 系統の反映込み） | 導入先の観測台帳（OBS-023）。レビュー 2 系統の反映を実装分と別に置いた Issue が乖離率 1.0 で当たった |
| 実機所見の修正 | 実装分の**前に**所見の裏取り 0.8h を置く | 導入先の観測台帳（OBS-034）。録画再現・報告者確認を積まないと 1.4 倍になる |
| 1 件で 8.0h 以上になる見積もり | **置かない**（Issue を分割するか、物量で根拠を書き直す） | 較正母集団で AI 予定 8.0h 以上の 13 件は**帯内 0 件**、乖離率の中央値 0.38（11 件が過大側） |
| 静的検出器・ゲートの新設 | 実装分に加えて、下の「偽陽性潰し分」を別項目で積む（実装分の 1.0〜1.5 倍）。Bash のコマンド文字列を解釈する検出器（区間分割・リダイレクト・インタプリタ本文・cd 追跡）は、回避形への対応を 2 巡と、分割の閾値を超えたときのライブラリ化 1 項目を積む | 観測台帳 OBS-097（3 件の実測。積まなかった回は乖離率 2.25。コマンド文字列型は回避形が 4 軸で独立に出て、係数を積んでも乖離率 2.50） |

## 積み方と補正

`effort_ai_planned` は **実装分 + レビュー対応分** の和として組み立てる。一括で 1 つの数値を置くと、レビュー指摘 0 件の Issue でしか当たらない（OBS-090）。静的検出器・ゲートを新設する Issue だけは **偽陽性潰し分** を加えた 3 項目の和にし、`effort_basis` の内訳にも 3 項目を書く。

- **実装分**: 変更対象ファイルへの編集そのもの
- **偽陽性潰し分**: 書き上げた検出規則を既存資産の**全体**へ当て、正当な同型が引っかかる偽陽性クラスを洗い出して条件を狭めるぶん。レビュー指摘を起点としないので、レビュー対応分に畳むと工数がまるごと消える（OBS-097）
- **レビュー対応分**: クロスモデルレビューを受けて fix commit を積むぶん。**直前にマージした同種 Issue の実績で補正する**:
  1. `gh issue list --state closed --search "<類似領域のキーワード>" --limit 5 --json number,body` 等で、同種（同じファイル領域・同じ変更の質）の直近 closed Issue を 1 件選ぶ。候補は `effort_ai_actual` が数値で記入され、かつ `effort_ai_planned` が 0 より大きいものに限る（未記入・非数値・複数 PR で実績が加算途中のものは飛ばす）
  2. 補正元の `effort_basis` に「実装分 X + レビュー対応分 Y」の内訳が**ある**場合: 実績比 = max(0, (`effort_ai_actual` − X) ÷ X) を自分の実装分に掛けてレビュー対応分にする。内訳のある補正元で乖離率（`effort_ai_actual ÷ effort_ai_planned`）をそのまま使うと、乖離率が 1 に近づいて「補正なし」に倒れる
  3. 内訳が**ない**（旧形式の）場合: レビュー対応分 = 実装分 × (`effort_ai_actual ÷ effort_ai_planned` − 1)
  - どちらの経路でも、計算結果が 0 以下なら 0 を採用せず下の既定値を使う
  - 補正元がレビュー指摘 0 件で終わった同種 docs Issue なら、既定値ではなくその実績比を使う（往復分 ≒ 実装分の 1/3 以下）。既定値を純追加の文言 Issue に当てると過大側へ倒れる
  - **補正元が見つからない場合の既定値**は、先に「**レビュー指摘の fix が実装・ゲートのロジックの作り直しを伴うか**」を問い、下の表で選ぶ。`/close-issue` の乖離率の帯（`0.71`〜`1.40`）は事後判定の指標で、既定値の根拠には使わない

| fix の中身 | レビュー対応分（既定値） | 出所 |
| ---------- | ------------------------ | ---- |
| 文言・ファイルの再置換で済む（契約針の差し替え・要約再掲文書の同期・案内文の更新・コード 0 行の純削除） | 実装分の **1/3〜1/2** | 観測台帳 OBS-160（実測 3 件で昇格し以後も再発。指摘はあっても 1 巡で収束し、同額で積んだ回は乖離率 0.14〜0.43）と導入先の観測台帳（純削除を同額で積んで過大側へ倒れた 3 件） |
| 実装の作り直しを伴う（通常の実装・修正） | 実装分と**同額** | OBS-111（クロスモデル 2 系統 + fix 1 巡の実費が実装と同額になった実測） |
| 検査・ガードの新設で、偽陽性潰し分を積まないもの（レビュアが新ガード自身の fail-closed 性・テストの実効性を問い、fix のたびに新しいレビュー面が増える） | 実装分の **1.5 倍以上**（下限） | 導入先の観測台帳（3 件の実測で乖離率 1.375〜2.50。同額で積んだ 1 件でも 2.40 で、3 巡のうち 2 巡は前巡の fix 自身が持ち込んだ欠陥）。上表の「静的検出器・ゲートの新設」で偽陽性潰し分を別項目に積んだ回は、レビュー対応分を同額のままで帯内に収まった（OBS-111）ので、その行には重ねない |

表の 3 行と上の「指摘 0 件の同種 docs Issue」の比率は、どれも「既定値 1 本が一方向へ倒れる」同じ失敗モードの別ケースで、分岐は fix が何を作り直すか（再置換で済むか・実装か・新しい面か）で決まる。補正元が見つかったときは表より補正元の実績比を優先する。

積み方の補足（どちらも上の和の内訳に書く。和に新しい項を足すのではない）:

- **再掲文書の同期分**: 規則・境界の文言を変える Issue は、同じ規則を再掲する生存文書を `grep` で数え上げ、その本数（うち version claim を持つ仕様書の本数）を実装分の内訳に別項目で積む（OBS-079。変更は regex 1 行でも再掲 5 本・うち仕様書 2 本の version bump と Changelog が要り、乖離率 1.50）
- **並列を計画する Issue**（実装の別エージェント委譲・レビュー複数レーンの同時起動）: 直列前提の積み上げ（各項目を順に足した値）をそのまま採用せず、同時に進む項目は長い方だけを積み、その壁時計の圧縮を `effort_basis` に明記する。複数レーンの指摘が 1 つの核へ収束して 1 往復で吸収された回は、実装中心の PR でも乖離率 0.25〜0.40 だった（OBS-160）

## 幅

規模を確定できない要素（分離の手掛かりが薄い・実機検証の周回数が読めない等）は幅を明示して積み、選んだ理由を `effort_basis` に残す（1 点に丸めない）。read-only の検索 1 回で確定する不確実性は、幅に積まずその場で確かめる。
