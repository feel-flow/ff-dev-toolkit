# 工数の推定（/create-issue）

`/create-issue` の SKILL.md 手順 3「工数の推定（KPI 計測）」で工数ブロックを書くときに読む（毎回）。単位・非対話モードでの扱い・ブロックの契約は SKILL.md が正本で、ここには過去実績の引き方・目安の値・積み方だけを置く。本文中の「手順 N」は SKILL.md の手順を指す。

## 過去実績の参照（3 層すべて）

過去の予実を **3 層すべて**から引く。1 つでも欠けると「記録するだけで参照されない層」ができる。

| 層 | 参照先 | 引き方 |
| ---- | ------ | ------ |
| 知見 | ACE Playbook の `estimation` カテゴリ | `PLAYBOOK.md` の索引テーブルを**カテゴリ列 `estimation` で絞って**引く。手順 2 の対象領域の検索とは別枠（キーワード一致では見積もり知見は偶然一致したときしか出ない） |
| パターン | `docs/08-knowledge/OBSERVATIONS.md` | 見積もり語彙（工数・見積もり・乖離・過小・過大）で検索し、`Kind: problem` と `Kind: keep` の**両方**を見る |
| データ | closed Issue の工数ブロック | `gh issue list --repo "$expected_repo" --state closed --search "<類似領域のキーワード>" --limit 30 --json number,title,body,closedAt` を実行し、`ff-effort` ブロックを読む |

MCP: 取得値: MCP で同じ repo の state / label / 検索語に合う number / title / body / labels / state / url を取得し、合計補正の候補にはクローズ日時（`closed_at` / `closedAt`）も取得する。検索結果に無ければ Issue の詳細を取得する。形式: 明示した上限 / 全 page の JSON、候補本文は全文。渡し先: この段の候補選択 / 見積もり根拠へ渡す。不足時: 重複探索は必須不足 / 上限到達で停止。見積もり用の任意履歴は取得不能と記録して継続。

`Kind: keep`（当たった見積もり方）を無視して `problem`（外した例）だけを見ると、補正が「バッファを積む」方向へ一方向に偏り、系統的な過大見積もりになる。

引いた結果は、**見つからなかった経路も含めて** `effort_basis` に残す。参照先が存在しないプロジェクトでは、その経路を「参照先なし」として扱い、見積もりは続行する。

## 人間工数の目安

**2026-09-10 に 3 リポジトリ・母集団 78 件で較正済み**（較正は人日で行い、表の値は 1d = 8h で人時へ換算したもの）。人間工数の実績は原理的に取れないので、行の値を直接反証するデータは無い。再較正の発火条件と手順は `/retrospective` の [references/effort.md](../../retrospective/references/effort.md)「集計レポートの実行（較正トリガの唯一の発火点）」が正本。

| 規模の目安 | 人間工数 |
| ---------- | -------- |
| 1 行の文言・リンク修正（ゲート 1 周で終わる） | 2.4h |
| 1 ファイル・数行の修正、文言変更 | 4.0h |
| 1 機能の追加（既存パターン踏襲、テスト込み） | 8〜24h |
| 新規スキル / モジュール 1 本 + ゲート + テスト | 24〜40h |
| 複数コンポーネント横断、設計判断を含む | 40〜80h |
| それ以上 | Issue を分割する（SKILL.md 手順 4「単一責務か」） |

**行は「設計判断を含むか」の語感ではなく、変更の物量で選ぶ**（触るファイル数・新規ファイルの有無・ゲート追加の有無）。較正母集団では、人間予定の中央値が 8h（30 件）から 32h（16 件）へ 4 倍になっても、AI 実績の中央値は 4.4h → 4.0h でほぼ動かなかった。動いたのは AI 予定（3.2h → 10.0h）で、上位行を選んだ Issue ほど AI 工数が人間工数に引きずられて置かれていた。

決定 Issue（論点を後で決める前提で起票した Issue）に着手するときは、未決の論点数を数え直して AI 予定を見直す。起票後に論点が個別の ADR・PR で決着し、着手時点では集約・記録・文書同期だけが残っていることがある（導入先の観測台帳 OBS-011。定例での分類・後続 Issue の分割を積んだまま着手した回は乖離率 0.17）。新規 ADR と移行・互換契約の策定そのものがこの Issue の仕事である設計専用（docs-only）は、後続実装を新しい bundle に分けるときも分けないときも、上の表の「新設 ADR・移行・互換契約の設計専用 docs Issue」行で積む。着手時に、別の ADR・PR で決着済みの論点を外し、残っている策定の物量をこの行で積み直す。未決の論点数だけを数える決定 Issue の見直しや、決定後の同期の行へは寄せない。

## 設計判断が済んだ実装の合計を補正する

着手時点で設計判断が確定し、残りが承認済みの仕様や実装計画などを写すだけの実装なら、**実装分とレビュー対応分の合計**を同種 Issue の実績で補正する。設計判断の有無は下の「積み方と補正」と同じ基準で判定する。本番リリースなど、同じ範囲に専用の積み方がある場合は、そちらを優先する。静的検出器・ゲートの偽陽性潰し分や bundle の固定費は、それぞれの規定に従い別に積む。

1. 同じリポジトリの同じファイル領域で、変更の質と物量が近く、着手時点で同じく「写すだけ」だった closed Issue を探す。`effort_ai_actual` が正の数値で、実績の加算が完了している候補を使う。SKILL.md 手順 3 に従って実績を人時にそろえる。単位の宣言と値が食い違う候補や、起票後の追加作業・専用の積み方で別に計上する作業を実績から切り分けられない候補は飛ばす。残りは検索の表示順で選ばず、取得したクローズ日時で比較し、**最も新しい 1 件**を選ぶ。適格な候補の日時が取れず比較できないときは、補正元を確定できないものとする。
2. 補正元の実績のうち、今回の実装分とレビュー対応分に当たる値を合計の基準とする。別項目で積む分も含めた予定全体に、最小 1.0h と 1 件で 8.0h 以上を置かない既存規定を適用する。最終的な予定のうち実装分とレビュー対応分に当たる額を、部品・作業ごとの既定値を比として配る。丸めた内訳の和を最終的な予定にそろえ、レビュー対応分の実績比や既定値を別に足さない。`effort_basis` には補正元の Issue 番号・採用した実績値・配分後の内訳を残す。
3. 条件に合う補正元が見つからなければ、従来どおり既定値で積み上げる。下の先勝ち表の「起票前に原因の調査と設計が済んでいて、写すだけの実装」に当たる場合は、このときレビュー対応分を実装分の **1/3** にする。補正元がある場合の合計にはこの行を重ねない。

導入先の観測台帳 OBS-078（Count 3）では、いずれも設計判断の承認が済んでいたが、部品の既定値を足して合計を置いたため過大側に外れた。乖離率は AI 実績 ÷ AI 予定。

| 変更 | AI 予定 | AI 実績 | 乖離率 |
| ---- | ------- | ------- | ------ |
| 秘匿規則の作り直し | 7.0h | 2.6h | 0.37 |
| 配信・除外・投稿の改修 | 7.0h | 2.1h | 0.30 |
| 要約版の追加 | 4.0h | 1.3h | 0.33 |

## 積み方と補正

`effort_ai_planned` は **実装分 + レビュー対応分** の和として組み立てる。一括で 1 つの数値を置くと、レビュー指摘 0 件の Issue でしか当たらない（OBS-090）。静的検出器・ゲートを新設する Issue だけは **偽陽性潰し分** を加えた 3 項目の和にし、`effort_basis` の内訳にも 3 項目を書く（既存の判定に乗る検出器・ゲートも 3 項目で書き、偽陽性潰し分は上の表の該当行のとおり実数で積む）。

- **実装分**: 変更対象ファイルへの編集そのもの
- **偽陽性潰し分**: 書き上げた検出規則を既存資産の**全体**へ当て、正当な同型が引っかかる偽陽性クラスを洗い出して条件を狭めるぶん。レビュー指摘を起点としないので、レビュー対応分に畳むと工数がまるごと消える（OBS-097）
- **レビュー対応分**: クロスモデルレビューを受けて fix commit を積むぶん。上の「設計判断が済んだ実装の合計を補正する」に該当しない場合は、下の先勝ち表を先に見て、該当行がなければ **直前にマージした同種 Issue の実績でレビュー対応分だけを補正する**:
  1. `gh issue list --state closed --search "<類似領域のキーワード>" --limit 5 --json number,body` 等で、同種（同じファイル領域・同じ変更の質・**設計判断の有無**が一致する）の直近 closed Issue を 1 件選ぶ。候補は `effort_ai_actual` が数値で記入され、かつ `effort_ai_planned` が 0 より大きいものに限る（未記入・非数値・複数 PR で実績が加算途中のものは飛ばす）。加算予定行（下の「起票後に範囲を足すときの加算予定」）のある候補は、以下の式の `effort_ai_planned` を予定 + 加算予定の合計として読む
  2. 補正元の `effort_basis` に「実装分 X + レビュー対応分 Y」の内訳が**ある**場合: 実績比 = max(0, (`effort_ai_actual` − X) ÷ X) を自分の実装分に掛けてレビュー対応分にする。内訳のある補正元で乖離率（`effort_ai_actual ÷ effort_ai_planned`）をそのまま使うと、乖離率が 1 に近づいて「補正なし」に倒れる
  3. 内訳が**ない**（旧形式の）場合: レビュー対応分 = 実装分 × (`effort_ai_actual ÷ effort_ai_planned` − 1)
  - どちらの経路でも、計算結果が 0 以下なら 0 を採用せず下の既定値を使う
  - **設計判断の有無**: 自 Issue が設計判断を含むか、確定済みの判断を写すだけかを先に決め、補正元も同じ側から選ぶ。判断の出どころ（先行 bundle の ADR + spec・利用者の決定・既存 ADR）は問わず、着手時点で判断が確定していれば「写すだけ」とする（起票後に決着した判断も含む）。判断込みの補正元の実績比には判断そのものの往復が含まれるので、写すだけの実装へ持ち込むと過大側へ倒れる。一致する補正元が無ければ、補正元なしとして下の既定値の表から選ぶ（導入先の観測台帳 OBS-267。判断込みの補正元の比率を持ち込んだ実測 5 件がすべて過大側で乖離率 0.26〜0.45。レビューが 2 巡に増えた回と、先に確定していたのが利用者の判断だった回を含む）。人間工数の表の行を物量で選ぶ規定とは対象が別で、そちらは変えない
  - 補正元がレビュー指摘 0 件で終わった同種 docs Issue なら、既定値ではなくその実績比を使う（往復分 ≒ 実装分の 1/3 以下）。既定値を純追加の文言 Issue に当てると過大側へ倒れる
  - **起票後に範囲が広がった補正元の扱い**: 記事・コンテンツ系などで補正元を選ぶとき、候補の `effort_evidence` に起票後の依頼による範囲の追加（追加分の内訳）が書かれている場合は、その追加分を除いた起票時スコープ相当の値（追加分を実績に含めず記録したものはそのままの値）で比べる。範囲が広がった作業を混ぜたまま補正元にすると乖離率が見積もり手法の当否を表さなくなる（導入先の観測台帳 OBS-290、4 件の実測）。加算予定行（下の「[起票後に範囲を足すときの加算予定](#起票後に範囲を足すときの加算予定)」）のある候補は、乖離率を予定 + 加算予定の合計で読む
  - **補正元で見積もった Issue の完了時の記録**: 補正元の実績比で見積もった Issue（比を減じた Issue を含む）は、完了時に `effort_evidence` へ実績の内訳（実装分とレビュー対応分）と範囲の変化の有無を残す（`/close-issue` の [effort.md](../../close-issue/references/effort.md) の「補正元で見積もった Issue の書き戻し」）。次にこの Issue を補正元として選ぶ人が、減じた比が当たったのかを内訳から読めるようにするため
  - **レビュー対応分の先勝ち**は、補正元の有無より先に下の表を見る。条件が真になる行があればその行を採る（develop → main の本番リリースは、直近の同形リリースが補正元の条件を満たしてもレビュー対応分を積まない）。どの行も真でなければ、補正元があるときはその実績比を使い、無いときは「**レビュー指摘の fix が実装・ゲートのロジックの作り直しを伴うか**」を問うてその下の表で選ぶ。`/close-issue` の乖離率の帯（`0.50`〜`2.00`）は事後判定の指標で、既定値の根拠には使わない

積み方の補足（いずれも上の和の内訳に書く。和に新しい項を足すのではない）:

- **再掲文書の同期分**: 規則・境界の文言を変える Issue は、同じ規則を再掲する生存文書を `grep` で数え上げ、その本数（うち version claim を持つ仕様書の本数）を実装分の内訳に別項目で積む（OBS-079。変更は regex 1 行でも再掲 5 本・うち仕様書 2 本の version bump と Changelog が要り、乖離率 1.50）
- **照合面の分**: 規律・運用の文書を変える Issue は、新しく書く主張のうち実装・toolkit・外部 API の挙動を述べるもの（「拒否されたら rc 3 で切り替わる」「直 push できる条件は X」等）を数え、そのうち照合で実体との食い違いが出る見込み件数に、**食い違い 1 件あたり 0.15〜0.6h** を掛けてレビュー対応分の内訳に別項目で積む。見込み件数は既定で主張数の 1/3（暫定。次回の較正で見直す）。レビューの往復は主張の数ではなく、主張が実体と合っているかを照合し直す往復で伸びる。係数は導入先の観測台帳（OBS-147）の実測 3 件の超過分（実績 − 予定。1d = 8h で換算）をレビュー指摘の件数で割った値で、主張の総数は記録に無いため指摘 1 件を食い違い 1 件とみなした: 0.5h ÷ 3 件 = 0.17h 以下（再掲文書の同期分を分離できず混ざっているので上限値）/ 1.4d = 11.2h ÷ Warning 31 件（4 回転 + 部分再検証の合計）= 0.36h / 0.7d = 5.6h ÷ Warning 9 件（うち 6 件が主張と実体のずれ）= 0.62h。外部 API・別リポジトリの挙動を述べる主張は上端で積む。3 件とも積まなかった回で、過小側に乖離率 1.50〜3.00 で外れた。補正元（同種の規律・運用文書の Issue）があるときは、その実績比に照合の往復が含まれているので足さない。補正元が無く既定値の表で積むときだけ、この分を積む。再掲文書の同期分（既存の規則を写した文書の揃え）とは別に数え、二重に積まない
- **照合面と再置換の境界**: 規律・運用の文書を変える Issue で挙動を述べる主張を新しく書くものには、既定値の表の「文言・ファイルの再置換で済む」（実装分の 1/3〜1/2）を当てず、レビュー対応分は照合面の分で積む。再置換の既定を当ててよいのは、書き換えが既存の主張の差し替え・写しに留まり、新しく照合の要る主張を含まない場合だけ
- **並列を計画する Issue**: 下の「並列サブエージェント実装」で、同じ計測軸の実装・レビュー対応・統合を積む。壁時計の短縮は別に記録し、最長レーンだけを総人時として採用しない。複数レーンの指摘が 1 つの核へ収束して 1 往復で吸収された実測（OBS-160、乖離率 0.25〜0.40）は、修正の重複を除く根拠として使い、並列レーンの作業を消す根拠にはしない。

## 並列サブエージェント実装

「人間予定 ÷ 4」は使わず、実装・レビュー束とfix・controllerの統合を独立に積む。`effort_ai_planned` は人時換算の予定、`effort_ai_actual` は観測事実を添える人時換算の申告、`effort_wallclock_actual` は別の実測値である（記録の正本は [close-issue の工数実績](../../close-issue/references/effort.md)）。3 並列で25分ずつ動いた場合、最長25分を3体合計の作業量として転記しない。実時間は各担当の内訳を作る参考であり、人時換算の基準・担当数・重複除外を `effort_basis` に書く。

| 内訳 | 実時間ベースで確かめるもの |
| --- | --- |
| 実装分 | agent 1体あたりの作業範囲・実時間を積む。原典の規模別15〜35分は同条件の参考値で、複数体なら各担当分を数える |
| レビュー対応分 | レビュー束1回の各担当分 + fix 1巡。原典の30〜40分はレビュー束とfixの参考値で、担当数と重複を確認する。同じ修正の重複計上を除く |
| controller分 | マージ・AC照合・ACE等の15〜20分は参考値。bundleでは共通固定費として親へ1回だけ置く |

例: 実装2体 × 25分 + レビュア4体 × 5分 + fix担当30分 + 親15分 = 担当別の活動時間の参考115分（約1.9h）。完全に重なる実装・レビューの壁時計は25 + 5 + 30 + 15 = 75分（約1.3h）で、両者を区別する。活動時間1.9hも人時換算の実績へ自動転記しない。予定へ採用する人時換算の基準と、待ち時間を含める範囲を明記する。

staging検証・配布などを人間だけが担当し、当該AIのAC・担当から外れるなら、その作業時間はAI予定へ入れず `effort_deploy` に担当・反映先・成否確認を書く。AIが担当する起動・待機・確認・申し送りの分はAI予定に残す。ACに含む検証を「マージ後だから」と省かず、後段へ移すならACと責任の境界を記録する。

### 直列見積もりから補正する場合と先行成果物の減算

実時間の同種データが無く、直列の人時換算見積もりから始める場合だけ、ファイル境界で分割できる**執筆分に0.5〜0.6を掛ける暫定候補**を検討する。同じ人時換算基準の比較実績が根拠で、担当数だけを理由に機械的に掛けない。レビュー対応・ゲート・統合・申し送りへ掛けない。実時間ベースですでに積んだ項目や同種の実績比で補正済みの項目へ重ねず、どちらの方法を選んだかを書く。根拠不足なら係数を適用せず幅を残す。

- **並列サブエージェントで実装する bundle における子の実装分と固定費**: 並列のサブエージェントで複数ファイルを並行実装する bundle では、子の実装分は並列作業で畳み込まれる（実測 **0.33〜0.37 倍**。兄弟が入れる共通判定を共用できる場合に共有分を差し引く規則［観測台帳 OBS-516］とも矛盾せず、共有できる判定を差し引いたうえで並列の作業量を積む。両者を二重に値引きはしない）。一方、**固定費は並列化で縮まないため別建てで積む**（下の「bundle の固定費と子の内訳」の式で親へ 1 回だけ置き、子へ二重計上しない）。

先行bundleのAPI契約・ADR・RPCの意味論、既存の画面部品・判定・テスト土台を実在確認し、今回作る残差だけを積む。Epic起票時と着手時で前提が変わったら、着手チェックで確認し、既存の予定と `effort_basis` は保存して本文へ差分の根拠と今回の参考内訳を追記する（既存値の遡及書き換えをしない）。後段へ移った検証は上の責任境界も併記する。

根拠は[並列見積もりの公開提案](https://github.com/feel-flow/ff-dev-toolkit/issues/134)に記録された導入先の観測台帳 OBS-136。2026-10-08の初期10件は、原典内の導入先Issue番号5327 / 5331 / 5323 / 5330 / 5335 / 5338 / 5337 / 5339 / 5336 / 5340の順に乖離率0.22 / 0.20 / 0.19 / 0.30 / 0.25 / 0.20 / 0.23 / 0.25 / 0.18 / 0.20。最後の3件は予定6.0 / 6.0 / 7.5h、実績1.5 / 1.1 / 1.5h。これらは原典の報告値で、担当別時間の再測定値ではない。後続コメントでは3並列bundleの1.5hをwallclockと明記しており、総人時へ転用しない。一方、2体分とレビュー束を積んだ予定2.0hに実績1.5 / 1.8hの例もあり、一律の短縮係数へ一般化しない。

## bundle の固定費と子の内訳

`--bundle` で子を束ねるとき、既存 Issue を bundle の子へ付け替えるときは、この節を先に適用する。単独 PR 前提の子の予定を単純合算しない（OBS-228 の実測 3 件 / ACE-1744-2）。

- **固定費（ブランチ作成・PR 作成・全件ゲート・レビュー・cleanup）は、次の和で積む式を使い、bundle では共通固定費として親へ 1 回だけ置く（子へ二重計上しない）**。単独 PR でも共通固定費は同じ式で別建てにし、bundle でも「1 回分」へ固定で圧縮しない（OBS-509。固定費の未計上や全件ゲート 1 回分の見込みで乖離率 2.30〜2.67 が再発した）。レビューを起動して結果を読む共通作業と、子の指摘を直す作業は区別する。固定費は bundle で 1 回だけ数え、子ごとに数えない:
  - **全件ゲートの回数（見込むレビュー巡回数 + 1）× 1 回の所要**（提出前とレビュー各巡の修正後の再確認。WSL 等を経由する環境ではその実行所要も含める）
  - **レビューの層（照合役・セルフレビュー・差分の再レビュー）の数** × 各層の起動・読み取りの所要（親が統括する共通作業。bundle で下の「子のレビュー対応分」へ 2 巡目以降の起動・読み取りを入れた場合、または単独 PR でレビュー対応分へ再レビューを含めた場合は、同じ再レビューを親や単独の固定費へ重ねて二重計上しない）
  - **セキュリティに関わる変更なら、専用セキュリティゲートの巡回** × 各回の所要（該当しない変更では 0）
- **子は実装分 + レビュー対応分に留める**。静的検出器の偽陽性潰し分は従来どおり子の内訳へ残す。実装・レビュー指摘の修正・偽陽性潰しの 3 項目を、この節と close-issue では「実装分」と総称する。
- **子のレビュー対応分は、束ねた PR のレビュー対応 1 回分を子の実装の比で配って決める**。1 回分は、束ねた PR 全体で見込む巡回数 × 1 巡あたりの指摘の修正量で積む。1 巡あたりの修正量は同種の束ねた PR の実績（巡回数と各巡の修正の時間）を補正元にし、補正元が無ければ何巡・1 巡何 h と見込んだ根拠を親子の `effort_basis` に書いて、下の「幅」に従い幅を残す。1 巡目の起動と読み取りは固定費として親に置き、2 巡目以降の起動と読み取り・各巡の指摘の修正を 1 回分に入れる。配る比は子の実装（偽陽性潰し分を含み、レビュー対応分を除く）の見積もり比とする。割り切れない端数は、この 1 回分に限り親ではなく最も大きい子で調整し、配った合計を 1 回分に保つ。
- **子ごとに単独 PR の倍率を掛けて足さない**。上の「積み方と補正」の既定値の表の倍率や、単独 PR を補正元にした実績比は、1 本の PR の大きさで較正した比である。子ごとに掛けても子の実装の合計に掛けても、修正が束ねた実装の合計に比例して増える前提になるが、束ねた PR では各巡の修正を子が分け合い、比例しなかった（導入先の観測台帳 OBS-198。子ごとにレビュー対応を実装の 1.5 倍で積んだ bundle は子 3 件の乖離率が 0.32〜0.33、全体の実装分を子へ比で配った bundle は親子 3 件とも帯内）。
- **bundle 親の工数ブロックには固定費だけ、子には各自の実装分だけを記録する**。束ね全体の合計は親の本文に参考値として書き、親の `effort_ai_planned` / `effort_human_planned` へ子の合計を再計上しない。各 `effort_basis` に親子の番号・固定費の記録先・自分の内訳を明記する。起票後に bundle 本文へ足した範囲は、親の加算予定行に置き、その実装の実績も親へ書き戻す（下の「起票後に範囲を足すときの加算予定」）。
- 新規の見積もりで最小 1.0h を適用する単位は bundle 全体であり、親子それぞれを 1.0h へ切り上げない。内訳は正の値を小数第 1 位まで記録し、丸めの端数は親で調整して合計を保つ。0.1h 未満の項目は別の子として分けず、同じ検証単位へ束ねる。
- **既存 Issue の予定値と `effort_basis` は遡って書き換えない**（遡及付与しないのはこの書き換えに限る）。単独 PR 前提で積んだ固定費を識別し、bundle 本文に今回の実装分の比と固定費 1 回分を追記して、元の予定との対応を残す。
- `ff-effort` ブロックの無い既存 Issue へ着手するときの見積もり追記は [git-workflow のステップ2](../../../docs-template/05-operations/deployment/git-workflow.md#ステップ2-ブランチ作成) に従う。

例: 共通固定費 1.0h、子 A の実装分 1.0h、子 B の実装分 2.0h なら、AI 予定は親 1.0h・A 1.0h・B 2.0h、束ね全体 4.0h。親に 4.0h を置いて子の 3.0h と二重計上しない。人間予定も独立に推定した同じ内訳方式で置く。

例（子 3 件のレビュー対応）: 子 A・B・C の実装が 2.0h・1.5h・1.5h（計 5.0h）で、束ねた PR のレビューを 2 巡、1 巡あたりの修正を 1.0h と見込むと、レビュー対応の 1 回分は 2.0h。実装の比 2.0:1.5:1.5 で配って A 0.8h・B 0.6h・C 0.6h とし、子の実装分（総称）は A 2.8h・B 2.1h・C 2.1h（計 7.0h）。子のレビュー対応分の合計 0.8 + 0.6 + 0.6 = 2.0h は 1 回分と一致する。子ごとに単独 PR の倍率（例: 2 巡を前提にした実装の 1.5 倍）で積むと、レビュー対応分だけで 3.0 + 2.25 + 2.25 = 7.5h になり、束ねた PR の 2 巡に対して子ごとに 2 巡ずつ、計 6 巡分の修正を積むことになる。親には上の例と同じく固定費だけを 1 回置く。

## 起票後に範囲を足すときの加算予定

起票後に同じ Issue へ AC・作業を足すとき、作業を部分 PR に分け直すとき、部分 PR を足すときは、起票時の `effort_ai_planned` と `effort_basis` を書き換えず（上の bundle の節の、既存の予定値を遡って書き換えない規則と同じ）、足した分の予定を加算予定行として工数ブロックへ 1 行足す。書式は次の 1 通りで、`/close-issue` の [effort.md「加算予定」](../../close-issue/references/effort.md#加算予定effort_ai_planned_added) と同じである（乖離率の出し方と完了報告の書き方の正本はあちら）:

```markdown
- effort_ai_planned_added: +N.Nh（YYYY-MM-DD <経路と件数>。<根拠 1 行>）
```

足す時機は、範囲を足した時点（その分の実装を始める前）とする。実装した後に実績を見てから足すと、乖離率が見積もりの当否を測らなくなる。

| 経路 | 足し方 |
| --- | --- |
| 本文の AC を追記する（`/out-of-scope-issue` の本文への追記、手での追記） | 同じ本文の書き込みで加算予定行を足す。工数ブロックが無い Issue にはブロックを新設しない |
| コメントで AC・作業を足す（`/out-of-scope-issue` と `/retrospective` の既定の経路） | コメントに `追記分の予定（目安）: +N.Nh` を書く（宣言の無い旧ブロックは `+N.Nd`）。本文の加算予定行は着手する側が写す |
| 着手する（bundle の子・本文・コメントを全件読んだとき）、着手後にコメントで追記を受けたとき | 本文の加算予定行に写っていない追記（目安を書いたコメント・目安の無い AC の追記）があれば、その分の実装を始める前に行を足す。目安が無ければここで見積もる |
| 作業を部分 PR に分け直す・部分 PR を足す | その時点で、起票時の予定に含まれていない分（足した作業の実装分 + レビュー対応分と、PR を分けて増える固定費）を足す。起票時の範囲を分け直しただけなら、PR を分けて増える固定費だけを足す |

- **足す先は、AC・作業を足した Issue の工数ブロック**とする。bundle では、子にブロックがあり子の AC・作業が増えたなら子のブロックへ、そうでなければ bundle 本文のブロックへ足す。bundle 本文へ足した分は、その実装の実績も親へ書き戻す（`/close-issue` の effort.md の bundle の節。予定と実績を同じ Issue にそろえる）
- **1 行に書く値は 1 つ**。目安を 2 件写すときも 2 行に分ける（`+3.0h + 4.0h` のように 1 行へまとめると、集計器は読めない行として扱う）

- **見積もり方は新規の見積もりと同じ**（実装分 + レビュー対応分。上の「積み方と補正」）。同じ PR に入る追記には固定費を重ねず、部分 PR を足すときは PR ごとの固定費（上の「bundle の固定費と子の内訳」の式）も積む。最小 1.0h の切り上げは当てない（起票時の予定に足す差分なので、正の値を小数第 1 位まで書く）。値の単位はブロックの宣言どおり（宣言の無い旧ブロックは `+N.Nd`）
- **範囲を足すたびに 1 行**足し、既存の行を書き換えない（集計器が複数行を合計する）。根拠には、追記したコメント・本文の日付と件数を書き、着手する側が写し済みかを照合できるようにする
- **範囲が縮んだときは、負の値の行で引かない**。完了時に `effort_evidence` へ書く（`/close-issue` の effort.md）
- 乖離率は `実績 ÷ (予定 + 加算予定の合計)` で出る（集計器 `effort-report.sh` と `/close-issue`）。予定を足さないまま追記・部分 PR を重ねると、追記のたびに乖離率が積み上がり、見積もりの外れではない外れ値が較正の母集団に入る（導入先 2 件の観測台帳。AC の追記を重ねた bundle で乖離率 2.50〜19.00、部分 PR を重ねた単位で 3.33〜14.33）

## 幅

規模を確定できない要素（分離の手掛かりが薄い・実機検証の周回数が読めない等）は幅を明示して積み、選んだ理由を `effort_basis` に残す（1 点に丸めない）。read-only の検索 1 回で確定する不確実性は、幅に積まずその場で確かめる。
