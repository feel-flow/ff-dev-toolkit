# 起票（/create-issue）

`/create-issue` の SKILL.md 手順 5 で priority を判定するときから、手順 6 で本文を組み立てて起票するまでに読む（毎回）。本文中の「手順 N」は SKILL.md の手順を指す。ラベルの照合規則と起票コマンド（ステップ 3）はこのファイルの中で隣接させてあり、互いに分断しない — 途中から読んで素の `gh issue create` を叩かない。

## 起票手順（SKILL.md 手順 5〜6 の続き）

### 候補の照合規則（手順 5 の続き）

無ラベルの Issue は backlog 一覧で種別も優先度も読めない。一方、**存在しないラベル名を渡すと `gh issue create` 自体が失敗する**ため、ラベル名を直書きで固定することもできない（本スキルは複数プロジェクトで動く）。そこで **実在確認 → 存在するものだけ付与 → 省略したものは報告**（verify-then-skip）とする。

**照合と起票の実行は下の 3 ステップで、状態をシェル変数でコマンド間に持ち越さない単純コマンドの分割方式で行う。** 本手順は「何を候補にするか」を決めるところまでを担う。候補の系統は SKILL.md 手順 5 の表にある。

#### priority の判定基準

ラベル名はプロジェクト依存だが、判定の軸は共通にする。

| 段階 | 基準 |
|------|------|
| critical | 本番で実害が進行中（障害・データ破損・コンプライアンス違反が現在形） |
| high | 利用者に見える不具合、または開発全体をブロックする（品質ゲートが恒常的に赤、標準手順が実行不能） |
| medium | 通常対応。実バグ・整合性リスクだが実害は顕在化していない |
| low | リファクタ・保留可・実需要待ち |

迷ったら medium。

#### 報告の書き分け（「不在」と「照会失敗」を混同しない）

実在確認をパスしなかった候補は、**省略したラベル名と理由を手順 7 の完了報告に含める**。ラベルが付かなかったこと自体は起票の失敗ではないが、黙って落とすと「付いているはず」という誤解が残る。

判定材料はステップ 2 で単独実行する `gh label list` の終了コードと出力。理由は照会の結果で書き分ける。**「不在」と「照会失敗」を混同しない**:

| 照会の結果 | 報告する理由 |
|---|---|
| 成功（一覧を信用できる） | 対象リポジトリに存在しないため省略した |
| 失敗（非 0 終了・空出力・上限到達のいずれか） | **ラベル一覧を信用できなかった**ため、実在を確認できず省略した |

照会が失敗しただけなのに「存在しない」と断定すると、運用者が実在するラベルを再作成して重複ラベルが生える。なおラベルが 1 つも無いリポジトリも「照会失敗」（確認できなかった）に倒れる — 「本当に 0 件」と「一覧が取れていない」を出力から区別できないため、重複ラベルを生やさない側へ倒すのが既定。

本スキルはラベルを**作らない**（`gh label create` は実行しない）。ラベルを増やすべきだと判断したら、起票は済ませたうえでその提案を完了報告に書く。

#### ISSUE_TEMPLATE 節の pre-flight（fail-soft）

ラベルと同じ穴が起票内容にもある。`.github/ISSUE_TEMPLATE/<種別>.md` が必須にしている節（例: 撤退コスト試算）は、本文を直接渡す起票では丸ごと落ちうる。そこでテンプレートがあればその `## ` 見出しを列挙して本文と照合し、無ければ何もしない。実行点はステップ 1（本文が揃った直後）:

```bash
# 種別→ファイル名の対応: 新機能→feature / バグ修正→bug / リファクタリング→refactor /
# インフラ→infra / ドキュメント→docs / 汎用タスク→general_task
type_slug="{手順1で確定した種別のスラッグ}"
template_dir=".github/ISSUE_TEMPLATE"
template_file=""
if [ -d "$template_dir" ]; then
  if [ -f "$template_dir/${type_slug}.md" ]; then
    template_file="$template_dir/${type_slug}.md"
  else
    for tpl_file in "$template_dir"/*.md; do
      [ -e "$tpl_file" ] || continue
      case "$(basename "$tpl_file")" in
        *"$type_slug"*) template_file="$tpl_file"; break ;;
      esac
    done
  fi
fi
if [ -n "$template_file" ]; then
  grep '^## ' "$template_file" || echo "節見出しなし（pre-flight スキップ）"
fi
```

対象は `.md` テンプレートのみ（GitHub issue forms の `.yml` は対象外で、その形式しか置いていないリポジトリは常にスキップ経路に入る）。`.github/ISSUE_TEMPLATE/` ディレクトリが無い場合や、種別スラッグに一致するファイルが無い場合は何も出さず、以降のステップに影響しない。このブロックの非 0 終了はブロッカーではない（`grep` が見出しを 1 件も見つけない rc=1 を含め、そのまま起票へ進む）。出力された見出しのうち本文に無いものは「省略した節」として手順 7 の完了報告に列挙する（起票は止めない）。埋められない節は削らず、中身を「なし」と明記して残す。

### 起票の 3 ステップ

起票は、**状態をシェル変数でコマンド間に持ち越さない 3 ステップ**で実行する。各ステップは単独の Write / 単純コマンドで完結するため、複合コマンドを拒否する実行環境（worktree 隔離セッションのコマンドガード等）でもそのまま通る。付与するラベルは `gh issue create` 自体の argv に載り、実行ログがそのまま証跡になる。

#### ステップ 1: 本文を一時ファイルへ書く

本文は Write ツールで作業ツリー外の一時ファイル（セッションの scratchpad 等）へ書き、`--body-file` で渡す（heredoc でシェル変数へ組み立てない。空のファイルを渡さない — 空の本文は「作成済みだが中身の無い」Issue を黙って生む）。内容は SKILL.md 手順 6 の構造で組み立てる。

本文を書いた直後に、上の「ISSUE_TEMPLATE 節の pre-flight（fail-soft）」の bash ブロックを単独実行し、列挙された `## ` 見出しを今書いた本文と突き合わせる。

#### ステップ 2: ラベルの実在確認（単独コマンド）

```bash
# 対象リポジトリは起票対象から確定し、ユーザーが対象にした OWNER/REPO と一致することを
# 確認する。GH_REPO や cwd の暗黙値に任せない。以後の gh 操作すべてに --repo を付ける。
expected_repo="OWNER/REPO"
gh label list --repo "$expected_repo" --limit 200 --json name --jq '.[].name'
```

`--limit 200` は必須。省略時の既定は 30 件で、ラベルが 30 個を超えるリポジトリでは実在するラベルが「見つからない」と誤判定される（頻用ラベルほど後ろに来やすい）。

なお bash フェンスは呼び出しごとに別のシェルで走るため、`expected_repo` の宣言は**使うフェンスごとに繰り返す**（前のフェンスの宣言は残っていない。ステップ 3 の冒頭に同じ宣言があるのはそのためで、まとめて 1 箇所に括り出さない）。「状態をシェル変数でコマンド間に持ち越さない」とは、宣言と消費を同一フェンス内で完結させるという意味であって、宣言済みの変数を後続フェンスから参照してよいという意味ではない。

照合する候補は手順 5 で決めた type / priority の 2 系統（`--bundle` 指定時は `bundle` も加える）。実在照合はエージェントがこの出力を読んで行う。出力の行と各候補名を**行単位の完全一致**で照合し、一致したものだけを付与候補に残す（部分一致・前方一致で判定しない。ラベル名は空白を含みうる）。次のいずれかに該当する場合は「照会失敗」として扱い、候補を全件省略してラベル無しで起票を続ける（起票自体は止めない）:

- 終了コードが非 0（取得失敗）
- 出力が空（ラベルが 1 つも無いリポジトリと、絞り込みが機能しなかった場合を区別できない）
- 出力が 200 行に達している（打ち切られた可能性があり、その先にあるラベルの不在を主張できない）

#### ステップ 3: 起票（単独コマンド）

```bash
expected_repo="OWNER/REPO"
gh issue create \
  --repo "$expected_repo" \
  --label "{実在を確認したラベル}" \
  --assignee "@me" \
  --title "{prefix}: {ストーリー要約}" \
  --body-file "{本文ファイルのパス}"
```

`--label` はステップ 2 の照合を通った候補の数だけ繰り返す（0 件なら渡さない）。

`gh issue create` の終了コードが 0 で Issue URL を取得できた場合だけ成功として扱う。失敗した場合は成功形式の報告を返さず、エラー内容と再試行方法を報告する。手順 7 で報告するラベル（付与・省略とその理由）は、記憶からではなく**実行した `gh label list` の出力と `gh issue create` の実行ログをそのまま読む** — 記憶で書くと、実際には付かなかったラベルを「付いた」と報告できてしまう。

**アサインについて**: 本スキルは着手前の起票ゲートなので、同梱の Git Workflow（`docs-template/05-operations/deployment/git-workflow.md` ステップ1）に従い `--assignee "@me"` を既定とする。`out-of-scope-issue` がアサイン中立なのは、あちらの起票が backlog 化であって着手ではないため — この非対称は意図的で、「便利だから」で揃えないこと。消費プロジェクトの Git Workflow が別の規定を持つ場合はそちらに従う。

> **重複について**: このラベル照合〜起票の手順は `out-of-scope-issue` の [references/filing.md](../../out-of-scope-issue/references/filing.md) §3.3 と意図的に同じ内容を持つ（違いは候補の系統と `--assignee` の既定だけ）。どちらも照合と報告の判定規則を起票コマンドと同じファイルの直前に置き、両者を分断しない（分断すると、起票コマンドだけを読んで実在確認ごと飛ばす経路ができる）。ドリフトは `tests/issue-label-contract/verify.sh` が両ファイルを突き合わせて検出する。**fixture に載せた契約行を片方だけ書き換える／削除すると red になる**（fixture 未収載の複製文までは検出しない）ので、変更は必ず両方へ入れること。
