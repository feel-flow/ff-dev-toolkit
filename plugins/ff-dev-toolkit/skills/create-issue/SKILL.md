# /create-issue — 仕様バリデーション付き Issue 作成支援

Issue を作成する際に、仕様の粒度チェックとタスク種別に応じた参照文書の自動提案を行います。

## プラグインルートの固定（必須）

<!-- ff-dev-toolkit-plugin-root-contract:start -->

## 前提

- プロジェクトに `docs/` 配下のコア文書（最小構成: MASTER・PROJECT・ARCHITECTURE の3文書）が存在すること（`/init-docs` で初期化可能）
- GitHub リポジトリが設定されていること

## 手順

### 1. タスク種別の確認

ユーザーに Issue の種別を確認してください。利用中のホストに構造化質問機能があれば使用し、なければ通常の対話で確認します:

- **新機能**: 新しい機能の追加
- **バグ修正**: 既存機能の不具合修正
- **リファクタリング**: コード構造の改善
- **インフラ**: CI/CD・デプロイ・インフラ変更
- **ドキュメント**: ドキュメントの追加・修正
- **汎用タスク**: テンプレ改善・CI・雑務など（general_task）

#### 非対話モード（確認を挟まない運用から呼ばれた場合）

呼び出し元が確認を挟まない運用（Issue 作成からマージまでを一気に進めるフルオート等）の場合、または依頼が「Issue 作って」のように起票の実行そのものである場合は、**種別・優先度・参照文書を会話コンテキストから推定し、確認なしで手順 2 以降へ進む**。

ヒアリングを必須にすると、自律フローからは構造的にスキップされる — 対話の往復を要求するスキルは呼ばれずに `gh issue create` の直接実行へ流れ、結果としてラベルも AC 粒度チェックも一切効かない Issue が量産される。発動しないゲートは無いゲートと同じなので、推定できるものは推定して起票まで到達させる。

推定してよいのは種別・優先度・参照文書まで。**受け入れ条件（AC）とストーリー要素の中身は推測で埋めない**（手順 4 の粒度チェックは非対話モードでも同じ基準で適用する。その第 5 項目「ストーリーが埋まっているか」も同様）。AC またはストーリー要素（ペルソナ/状況・動機・価値/結果）を書く材料が会話コンテキストに無い場合は、非対話モードでも止めてユーザーに確認する — ここを埋めるために創作すると、粒度チェックを通すためだけの偽の Issue ができ、ゲートが自分自身を無効化する。

推定した項目とその根拠は手順 7 の完了報告に 1 行で残す（例: 「種別=バグ修正（テスト失敗の報告から推定）／優先度=high（CI が恒常的に赤）」）。黙って推定すると、誤った種別・優先度が確認されないまま backlog に固定される。

### 2. 参照文書の自動提案

タスク種別に応じて、事前に読むべき文書を提案します:

| タスク種別 | 必須参照 | 推奨参照 |
| ------------ | -------- | -------- |
| 新機能 | MASTER, ARCHITECTURE, DOMAIN | PATTERNS, TESTING |
| バグ修正 | 関連 Issue, PATTERNS | TESTING |
| リファクタリング | ARCHITECTURE, PATTERNS | TESTING |
| インフラ | MASTER, DEPLOYMENT | ARCHITECTURE |
| ドキュメント | MASTER | 更新対象文書 |

提案例: 「新機能の Issue を作成します。事前に MASTER.md、ARCHITECTURE.md、DOMAIN.md を確認することを推奨します。」

#### 関連 ACE エントリの検索（Reuse）

ACE Playbook（`docs/08-knowledge/PLAYBOOK.md`）が存在する場合、索引テーブルを Issue の対象領域・キーワードで検索し、関連する ACE エントリを最大 3 件特定する。見つかったエントリは手順 6 の Issue 本文「参照文書」セクション内の「関連 ACE エントリ」小見出しに `ACE-ID: タイトル（リンク）` 形式で添付する。GitHub の Issue 本文では相対パスが解決されないため、リンクは blob URL（`https://github.com/<owner>/<repo>/blob/<default-branch>/docs/08-knowledge/playbook/<category>.md#<anchor>`）で書く。`<anchor>` は **ACE ID を小文字化**したもので、すべての ID 形式に適用する（`ACE-438-1 → #ace-438-1`、`ACE-i425-1 → #ace-i425-1`、`ACE-001 → #ace-001`）。label にタイトルを併記するのは Issue 可読性のための意図的な例外（PLAYBOOK 記述ガイドラインの `[ACE-XXX](...)` 統一形式はリポジトリ内文書間の参照向け）。実装者が着手時に過去の知見へ確実に到達できるようにするのが目的（書く側だけでなく読む側の導線）。関連エントリが無ければ添付しない（無理に紐付けない）。

#### 過去実績の参照（工数見積もりの Reuse）

手順 6 の工数見積もりブロックを書くため、過去の予実を **3 層すべて**から引く。1 つでも欠けると「記録するだけで参照されない層」ができる。

| 層 | 参照先 | 引き方 |
| ---- | ------ | ------ |
| 知見 | ACE Playbook の `estimation` カテゴリ | `PLAYBOOK.md` の索引テーブルを**カテゴリ列 `estimation` で絞って**引く。上の汎用 Reuse 検索とは別枠 — あちらは対象領域のキーワード一致なので、見積もり知見は偶然一致したときしか出ない |
| パターン | `docs/08-knowledge/OBSERVATIONS.md` | 見積もり語彙（工数・見積もり・乖離・過小・過大）で検索し、`Kind: problem` と `Kind: keep` の**両方**を見る |
| データ | closed Issue の工数ブロック | `gh issue list --repo "$expected_repo" --state closed --search "<類似領域のキーワード>" --limit 30 --json number,title,body` を実行し、`ff-effort` ブロックを読む |

`Kind: keep`（当たった見積もり方）を無視して `problem`（外した例）だけを見ると、補正が「バッファを積む」方向へ一方向に偏り、今度は系統的な過大見積もりになる。**非対称なフィードバックは非対称なバイアスを作る**ので、両方を見ること。

引いた結果は、**見つからなかった経路も含めて**手順 6 の `effort_basis` に残す（参照経路が実際に機能しているかを事後に検証可能にするため）。参照先が存在しないプロジェクトでは、その経路を「参照先なし」として扱い、見積もりは続行する。

### 3. Issue 内容のヒアリング（ストーリー収集）

種別に応じてストーリー要素を収集します:

- **ユーザー向け（新機能 / ドキュメント）= ユーザーストーリー**
  - ペルソナ（誰が）
  - 実現したいこと（何を）
  - 得られる価値／理由（なぜ）
- **技術系（バグ / リファクタ / インフラ / 汎用タスク（general_task））= ジョブストーリー**
  - 状況・トリガー（どんなとき）
  - どうしたい（動機）
  - 得たい結果（その結果）

加えて以下を収集します:

- **タイトル**: conventional-commit プレフィックス（`feat:`/`fix:` 等）+ ストーリー要約（汎用タスクのみ `【タスク】` 形式）
- **受け入れ条件**: 振る舞い（Given-When-Then）+ Definition of Done

#### 工数の推定（KPI 計測）

人間が実施した場合の工数と、AI エージェントで実施した場合の工数を推定する。単位は **`d`（人日。1d = 8h）固定**、小数第 1 位まで、最小 0.1d。時間単位（`h`）は使わない — 単位が混ざると集計が静かに壊れる。

**非対話モードでも推定してよい。** 手順 1 の非対話モード規定は「受け入れ条件（AC）とストーリー要素の中身は推測で埋めない」だが、**工数見積もりはこの制限の対象外**とする。見積もりは本質的に推定であって、材料が揃うまで待つ性質のものではないため。この非対称は意図的なので「AC と同じ扱い」に揃えないこと — 揃えると非対話起票で工数欄が空のまま量産される。

人間工数の目安（**暫定値**。実データが 20 件貯まった時点で実測分布から較正する。初期値は感覚値であり、この表自体が較正対象である）:

| 規模の目安 | 人間工数 |
| ---------- | -------- |
| 1 ファイル・数行の修正、文言変更 | 0.5d |
| 1 機能の追加（既存パターン踏襲、テスト込み） | 1〜3d |
| 新規スキル / モジュール 1 本 + ゲート + テスト | 3〜5d |
| 複数コンポーネント横断、設計判断を含む | 5〜10d |
| それ以上 | Issue を分割する（「重要ルール」の 1 Issue = 1 成果物） |

**AI 工数は「人間工数 ÷ 圧縮率」で導出しない。** レビュー往復・品質ゲートの実行・fix commit を織り込んで独立に推定する。除算で導くと圧縮率が定数になり、KPI が自己言及して何も測らなくなる。

**ask モード（オプトイン）**: 対話モードであり、かつユーザーが工数の確認を明示的に要求した場合に限り、推定値を提示して確認を取る。**既定は確認なしの推定**。質問を既定にすると、手順 1 が述べたとおり自律フローから本スキルごとスキップされる。

### 4. 受け入れ条件（AC）の粒度チェック

収集した受け入れ条件（AC）が以下の条件を満たしているか検証します:

- [ ] **具体的か**: 「〜が動くこと」ではなく「〜の場合に〜が返ること」のように具体的
- [ ] **検証可能か**: テストで確認できる表現になっている
- [ ] **単一責務か**: 1つの Issue に複数の独立した機能が混在していない
- [ ] **曖昧な表現がないか**: 「適切に」「正しく」「きちんと」等の曖昧語を排除
- [ ] **ストーリーが埋まっているか**: ペルソナ/状況・動機・価値/結果のいずれも空欄でない
- [ ] **AC が GWT+DoD 形式か**: 「振る舞い（Given-When-Then）」と「Definition of Done」の 2 ブロックで記述されている
- [ ] **DoD が指す既存成果物が実在するか**: 既存のファイル・ゲート・スクリプトの「更新」を含む DoD 項目がある場合のみ、対象の実在を作業リポジトリ内で `grep` 等により確認し、見つからなければ「更新」ではなく「新設」と書き分ける
- [ ] **具体値の出所が確認されているか**: AC に終了コード・HTTP ステータス・エラーコードなどの具体値を書く場合のみ、その値の出所で書き分ける。**(a) 既存実装の契約**を指す値は、シナリオと値の対応まで確認して引用する（`grep -n "exit(" scripts/<cli>.ts` は候補出しであって確認ではない — 別経路の値を掴む。既定はヒットした分岐に入ることをコードで読むことで、読み切れないときだけ実際に実行して終了コードを取る）。**(b) これから定める新しい契約**は、根拠（設計判断・既存の並び・仕様文書）を 1 行添えれば具体値のまま書いてよい。**(c) どちらでもない値**は数値を書かず、「拒否されること」のように**挙動**で書く

第 7 項（DoD が指す既存成果物の実在確認）の結果は、**手順 7 の完了報告に「DoD 実在確認: 済（対象 N 件）」または「DoD 実在確認: 対象なし」の 1 行で必ず残す**（N = 実在を確認した既存ファイル・ゲート・スクリプトの件数。「対象なし」= 既存成果物の「更新」を含む DoD 項目が無かった場合）。非対話モードでは実行者がこの確認を省略しても表面化しない — 実測では非対話起票の 3 Issue すべてが実在しないパスを DoD に記載し、close-issue 時に 3 回の本文訂正を要した。発動しないゲートは無いゲートと同じなので、確認の実施を報告面の契約で可視化する。

粒度が不十分な場合、改善提案を出してください:

```
⚠️ 受け入れ条件（AC）の粒度チェック

以下の基準が曖昧です:
- 「正しくバリデーションされること」
  → 改善案: 「メールアドレスが RFC 5322 に準拠していない場合、422 エラーを返すこと」

- 「適切にエラーハンドリングすること」
  → 改善案: 「DB接続エラー時に503ステータスとリトライ可能なレスポンスを返すこと」

出所が未確認の具体値 (1 件):
- 「両方指定した spec は exit 2 で拒否されること」（exit 2 が既存契約なのか新しく定める値なのか不明）
  → (a) 既存契約なら: 該当シナリオを実行して終了コードを取り（`<検証コマンド> <両方指定の spec>; echo $?`）、`grep -n "exit(" scripts/validate-spec.ts` の分岐と突き合わせる
  → (b) 新しく定めるなら: 「既存の usage error=2 / invalid input=1 の並びに合わせて 1」のように根拠を 1 行添える
  → (c) どちらも示せないなら: 「両方指定した spec は拒否され、どちらか一方だけを指定するよう促すメッセージが出ること」（数値を書かない）
```

> **`/refine-issue` との同期**: 上の項目リストは本スキルが正規ソースで、`/refine-issue` 手順 4 の対応表がその項目名を左列として写している。項目を増減・改名したときは同表も同時に直すこと。片方だけの更新は `tests/issue-label-contract/verify.sh` が両者の集合を突き合わせて red にする。

### 5. ラベルの決定（実在確認 → 存在するものだけ付与）

無ラベルの Issue は backlog 一覧で種別も優先度も読めず、「今どれを拾うべきか」の判断が Issue を 1 件ずつ開かないと下せなくなる。一方、**存在しないラベル名を渡すと `gh issue create` 自体が失敗する**ため、ラベル名を直書きで固定することもできない（本スキルは複数プロジェクトで動く）。そこで **実在確認 → 存在するものだけ付与 → 省略したものは報告**（verify-then-skip）とする。

付与を試みるのは次の 2 系統。具体的なラベル名は消費プロジェクトの分類に合わせる（下は代表例であり、この名前でなければならないという意味ではない）。

| 系統 | 決め方 | よくある名前 |
|------|--------|-------------|
| type | 手順 1 で確定したタスク種別を写す。タイトルの conventional-commit プレフィックスと食い違わせない | 新機能 → `enhancement`（`feat:`）／バグ修正 → `bug`（`fix:`）／リファクタリング → `refactor`（`refactor:`）／インフラ → `chore`（`chore:`）／ドキュメント → `documentation`（`docs:`）／汎用タスク → `chore`（`chore:`） |
| priority | 手順 3 のストーリーと背景から読み取れる影響範囲・緊急度を、下の基準に当てる | `priority:critical` / `priority:high` / `priority:medium` / `priority:low` |

`follow-up` 系のラベルは付けない。本スキルは**着手前の起票ゲート**であって、PR レビュー・実装から派生した発見の記録ではない（そちらは `out-of-scope-issue` が `follow-up` を付けて起票する）。

#### priority の判定基準

ラベル名はプロジェクト依存だが、判定の軸は共通にする。

| 段階 | 基準 |
|------|------|
| critical | 本番で実害が進行中（障害・データ破損・コンプライアンス違反が現在形） |
| high | 利用者に見える不具合、または開発全体をブロックする（品質ゲートが恒常的に赤、標準手順が実行不能） |
| medium | 通常対応。実バグ・整合性リスクだが実害は顕在化していない |
| low | リファクタ・保留可・実需要待ち |

迷ったら medium。

#### 報告の書き分け（「不在」と「照会失敗」を混同しない）

実在確認をパスしなかった候補は、**省略したラベル名と理由を手順 7 の完了報告に含める**。ラベルが付かなかったこと自体は起票の失敗ではないが、黙って落とすと「付いているはず」という誤解が残る。

判定材料は手順 6 で単独実行する `gh label list` の終了コードと出力。理由は照会の結果で書き分ける。**「不在」と「照会失敗」を混同しない**:

| 照会の結果 | 報告する理由 |
|---|---|
| 成功（一覧を信用できる） | 対象リポジトリに存在しないため省略した |
| 失敗（非 0 終了・空出力・上限到達のいずれか） | **ラベル一覧を信用できなかった**ため、実在を確認できず省略した |

照会が失敗しただけなのに「存在しない」と断定すると、運用者が実在するラベルを再作成して重複ラベルが生える。なおラベルが 1 つも無いリポジトリも「照会失敗」（確認できなかった）に倒れる — 「本当に 0 件」と「一覧が取れていない」を出力から区別できないため、重複ラベルを生やさない側へ倒すのが既定。

なお本スキルはラベルを**作らない**（`gh label create` は実行しない）。起票ゲートが消費プロジェクトのラベル体系を勝手に増やすと、分類の設計が Issue 単位で場当たりに膨らむため。ラベルを増やすべきだと判断した場合は、起票は済ませたうえでその提案を完了報告に書く。

**照合と起票の実行は手順 6 で、状態をシェル変数でコマンド間に持ち越さない単純コマンドの分割方式で行う。** 本手順は「何を候補にするか」を決めるところまでを担う。

> **重複について**: 手順 6 のラベル照合〜起票の手順は `out-of-scope-issue` §3.3 と意図的に同じ内容を持つ（違いは候補の系統と `--assignee` の既定だけ）。参照ファイルへ切り出さないのは、照合と報告の判定規則が起票コマンドの直前で読まれないと、実在確認ごと飛ばされる経路ができるから。ドリフトは `tests/issue-label-contract/verify.sh` が両ファイルを突き合わせて検出する。**fixture に載せた契約行を片方だけ書き換える／削除すると red になる**（fixture 未収載の複製文までは検出しない）ので、変更は必ず両方へ入れること。

#### ISSUE_TEMPLATE 節の pre-flight（fail-soft）

ラベルと同じ穴が起票内容にもある。`gh issue create --body` を直接呼ぶ運用は、`.github/ISSUE_TEMPLATE/<種別>.md` が必須にしている節（例: 撤退コスト試算、6 観点フレームワーク）をどこにも強制されずに丸ごと落とせる。そこでラベルと同じ **verify-then-skip**（テンプレートがあればその `## ` 見出しを列挙して本文と照合し、無ければ何もしない）を、起票直前に行う。

手順1で確定した種別に対応するテンプレートファイルを単独コマンドで確認する（見つからなければ fail-soft で何も強制せず起票を続ける）:

```bash
# 種別→ファイル名の対応: 新機能→feature / バグ修正→bug / リファクタリング→refactor /
# インフラ→infra / ドキュメント→docs / 汎用タスク→general_task
type_slug="{手順1で確定した種別のスラッグ}"
template_dir=".github/ISSUE_TEMPLATE"
template_file=""
if [ -d "$template_dir" ]; then
  if [ -f "$template_dir/${type_slug}.md" ]; then
    template_file="$template_dir/${type_slug}.md"
  else
    for tpl_file in "$template_dir"/*.md; do
      [ -e "$tpl_file" ] || continue
      case "$(basename "$tpl_file")" in
        *"$type_slug"*) template_file="$tpl_file"; break ;;
      esac
    done
  fi
fi
if [ -n "$template_file" ]; then
  grep '^## ' "$template_file" || echo "節見出しなし（pre-flight スキップ）"
fi
```

対象は `.md` テンプレートのみ（GitHub issue forms の `.yml` は対象外で、その形式しか置いていないリポジトリは常にスキップ経路に入る）。`.github/ISSUE_TEMPLATE/` ディレクトリが無い場合や、種別スラッグに一致するファイルが無い場合は何も出さず、以降のステップに影響しない。このブロックの非 0 終了はブロッカーではない（`grep` が `## ` 見出しを 1 件も見つけない場合の rc=1 を含め、fail-soft でそのまま起票へ進む）。テンプレートが見つかった場合は、出力された `## ` 見出しのうち手順6ステップ1で組み立てた本文に同名の見出しが無いものを「省略した節」として手順7の完了報告に列挙する（起票は止めない）。埋められない節は本文から削らず、その節の中身を「なし」と明記して残す（何を検討して空にしたかを追跡可能にするため）。

### 6. Issue の作成

検証をパスした内容で Issue を作成します。以下の構造を使用してください（先頭の見出しは種別に応じて `## ユーザーストーリー`〔ユーザー向け: feature/docs〕または `## ジョブストーリー`〔技術系: bug/refactor/infra/汎用タスク〕の**どちらか一方**を使う）:

```markdown
## ユーザーストーリー

[種別に応じたストーリー]

## 背景

[なぜ必要か]

## 参照文書

- [タスク種別に応じた参照文書リスト]

### 関連 ACE エントリ（該当時のみ）

- [ACE-XXX-X: タイトル](https://github.com/<owner>/<repo>/blob/<default-branch>/docs/08-knowledge/playbook/<category>.md#ace-xxx-x)
  <!-- Issue 本文では相対リンクが解決されないため blob URL で書く。fragment は ACE ID の小文字化（旧 3 桁 ID なら #ace-001 形式） -->

## 受け入れ条件（AC）

### 振る舞い（Given-When-Then）

- [ ] **Given** ... **When** ... **Then** ...

### Definition of Done

- [ ] [機械的完了条件]
- [ ] markdownlint エラーなし（該当する場合）

## 工数見積もり（KPI 計測）

<!-- ff-effort:begin -->
- effort_human_planned: [N.Nd]
- effort_ai_planned: [N.Nd]
- effort_ai_actual: (未記入)
- effort_basis: [手順 2 の 3 経路で引いた結果と規模の判断根拠。見つからなかった経路も書く]
<!-- ff-effort:end -->
```

工数ブロックの契約:

- マーカー行 `<!-- ff-effort:begin -->` / `<!-- ff-effort:end -->` は**この綴りのまま**書く。`/close-issue` の実績書き戻しと集計器 `effort-report.sh` がこの 2 行を境界として本文を切り出すため、綴りが違うと機械的に見えなくなる（エラーにはならず、静かに集計対象から落ちる）
- `effort_ai_actual` は起票時点では `(未記入)`。マージ直前に `/close-issue` が観測事実とともに書き戻す
- **乖離率は書かない**。`effort_ai_planned` と `effort_ai_actual` から導出できる値をブロックに置くと、実績が加算更新（1 Issue に複数 PR）されたときに静かに stale になる。乖離率は集計器と完了報告コメントがその都度計算する
- **`effort_human_actual` という項目は作らない**。人間は実際には作業しないので実績は原理的に取れず、人間側は永久に予定（反実仮想）である。項目を作ると「取れるはず」という誤解が残る

起票は、**状態をシェル変数でコマンド間に持ち越さない 3 ステップ**で実行します。各ステップは単独の Write / 単純コマンドで完結するため、複合コマンドを拒否する実行環境（worktree 隔離セッションのコマンドガード等）でもそのまま通ります。

#### ステップ 1: 本文を一時ファイルへ書く

本文は Write ツールで作業ツリー外の一時ファイル（セッションの scratchpad 等）へ書き、`--body-file` で渡す（heredoc でシェル変数へ組み立てない。空のファイルを渡さない — 空の本文は「作成済みだが中身の無い」Issue を黙って生む）。内容は上の構造で組み立てる。

本文を書いた直後に、手順 5 末尾の「ISSUE_TEMPLATE 節の pre-flight（fail-soft）」の bash ブロックを単独実行し、列挙された `## ` 見出しを今書いた本文と突き合わせる（比較対象の本文がここで初めて揃うため、実行点はこのステップ）。

#### ステップ 2: ラベルの実在確認（単独コマンド）

```bash
# 対象リポジトリは起票対象から確定し、ユーザーが対象にした OWNER/REPO と一致することを
# 確認する。GH_REPO や cwd の暗黙値に任せない。以後の gh 操作すべてに --repo を付ける。
expected_repo="OWNER/REPO"
gh label list --repo "$expected_repo" --limit 200 --json name --jq '.[].name'
```

`--limit 200` は必須。省略時の既定は 30 件で、ラベルが 30 個を超えるリポジトリでは実在するラベルが「見つからない」と誤判定される（頻用ラベルほど後ろに来やすい）。

なお bash フェンスは呼び出しごとに別のシェルで走るため、`expected_repo` の宣言は**使うフェンスごとに繰り返す**（前のフェンスの宣言は残っていない。ステップ 3 の冒頭に同じ宣言があるのはそのためで、まとめて 1 箇所に括り出さない）。「状態をシェル変数でコマンド間に持ち越さない」とは、宣言と消費を同一フェンス内で完結させるという意味であって、宣言済みの変数を後続フェンスから参照してよいという意味ではない。

照合する候補は手順 5 で決めた type / priority の 2 系統。実在照合はエージェントがこの出力を読んで行う。出力の行と各候補名を**行単位の完全一致**で照合し、一致したものだけを付与候補に残す（部分一致・前方一致で判定しない。ラベル名は空白を含みうる）。次のいずれかに該当する場合は「照会失敗」として扱い、候補を全件省略してラベル無しで起票を続ける（起票自体は止めない）:

- 終了コードが非 0（取得失敗）
- 出力が空（ラベルが 1 つも無いリポジトリと、絞り込みが機能しなかった場合を区別できない）
- 出力が 200 行に達している（打ち切られた可能性があり、その先にあるラベルの不在を主張できない）

#### ステップ 3: 起票（単独コマンド）

```bash
expected_repo="OWNER/REPO"
gh issue create \
  --repo "$expected_repo" \
  --label "{実在を確認したラベル}" \
  --assignee "@me" \
  --title "{prefix}: {ストーリー要約}" \
  --body-file "{本文ファイルのパス}"
```

`--label` はステップ 2 の照合を通った候補の数だけ繰り返す（0 件なら渡さない）。ラベル誤報告はこの形でも防がれる — 付与するラベルは `gh issue create` 自体の argv に載り、実行ログがそのまま証跡になる。

`gh issue create` の終了コードが 0 で Issue URL を取得できた場合だけ成功として扱う。失敗した場合は成功形式の報告を返さず、エラー内容と再試行方法を報告する。

**アサインについて**: 本スキルは着手前の起票ゲートなので、同梱の Git Workflow（`docs-template/05-operations/deployment/git-workflow.md` ステップ1）に従い `--assignee "@me"` を既定とする。`out-of-scope-issue` がアサイン中立なのは、あちらの起票が backlog 化であって着手ではないため — この非対称は意図的で、「便利だから」で揃えないこと。消費プロジェクトの Git Workflow が別の規定を持つ場合はそちらに従う。

### 7. 完了報告

作成した Issue の URL を表示し、次のアクションを提案してください。あわせて次を含めます:

- **付与したラベル**（`gh issue create` に実際に渡した `--label`）と、**省略したラベル名 + 理由**（照会の結果を手順 5 の表に当てて「不在」と「照会失敗」を書き分ける）。省略が無ければその旨は書かなくてよい。値は記憶からではなく**実行した `gh label list` の出力と `gh issue create` の実行ログをそのまま読む** — 記憶で書くと、実際には付かなかったラベルを「付いた」と報告できてしまう
- 省略理由が「不在」のラベルがある場合は、`/setup-github-labels`（ff-dev-toolkit 同梱。推奨ラベル構成の不足分だけを冪等に作成する）で整備できる旨を 1 行添える。「照会失敗」のときは添えない（実在を確認できていないのに整備を促すと、重複ラベルを生やす側へ倒れる）。整備はそのスキルの責務で、本スキルからは実行しない
- **省略した ISSUE_TEMPLATE 節**（手順5 の pre-flight でテンプレートが見つかった場合のみ）: `## ` 見出しのうち本文に無いものを「省略した節: …」の形で列挙する。省略が無ければその旨は書かなくてよい。`.github/ISSUE_TEMPLATE/` ディレクトリが無い／一致するファイルが無いリポジトリでは照合対象が無いため何も書かない
- **DoD 実在確認の結果（必須・1 行）**: 「DoD 実在確認: 済（対象 N 件）」または「DoD 実在確認: 対象なし」（手順 4 第 7 項の契約。この 1 行が無い完了報告は不完全として扱う — 実在確認の省略を報告面で検出可能にするため）
- 非対話モード（手順 1）で推定した種別・優先度と、その根拠（DoD 実在確認の行も同じ報告に並べる）
- **工数見積もり（必須・1 行）**: `工数見積もり: 人間 N.Nd / AI N.Nd（参照: 知見 X 件 / パターン Y 件 / データ Z 件）`。3 経路それぞれの参照件数を書く（0 件なら 0 と書く）。この行が無い完了報告は不完全として扱う — 参照経路を通らずに勘で書いた見積もりを、報告面で検出可能にするため

## 重要ルール

- 受け入れ条件（AC）が曖昧な場合は Issue を作成せず、改善を求めること
- 1 Issue = 1つの成果物を原則とし、スコープが大きい場合は分割を提案すること
- 参照文書が存在しない場合は、その旨を警告すること
- **受け入れ条件（AC）の内容**はユーザーの意図を推測で補完せず、不明点は確認すること。種別・優先度・参照文書は、非対話モード（手順 1）に限り会話コンテキストからの推定を認め、推定した旨と根拠を完了報告に残すこと
- **工数見積もりは非対話モードでも推定して埋めること**（AC・ストーリー要素とは扱いが異なる意図的な非対称）。見積もりは本質的に推定であり、確認を待つと自律フローから本スキルごとスキップされる。確認を取るのは ask モード（手順 3）に限る
- ラベルは実在確認をパスしたものだけを付け、省略したものは黙って落とさず報告すること（存在しないラベル名は `gh issue create` 自体を失敗させる）
