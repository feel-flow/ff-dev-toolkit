# /removal-sweep — 撤去 PR の 3 系統走査チェックリスト

機能・設定・UI 要素を撤去する PR は、コードの削除そのものより**残存参照の走査漏れ**で壊れる。
識別子の grep だけでは足りない — 撤去対象は「名前」以外にも**表示文言**と**構造セレクタ・モック応答**でリポジトリに結合している。この 3 系統は互いに独立した結合チャネルであり、**1 系統でも省略すると漏れる**（2 系統を実施して「残存参照なし」と明記した PR ですら 3 つ目のチャネルで漏れた実例がある）。

撤去 PR では以下の 3 系統を**すべて**実施し、系統ごとに使った grep 語と結果を PR 本文へ記載する。

## 前提

- 撤去対象（機能名・設定キー・UI 要素・フラグ等）が特定できていること
- 撤去の実装（削除 diff）に着手する前でも後でもよいが、**PR 作成前に必ず 3 系統を完走**すること

## 系統 1: 識別子

「何を消したか」を名前で探す。

- [ ] **camelCase / snake_case の両方**で grep する（`queryRewrite` と `query_rewrite` は別ヒット。API 境界・DB スキーマ・イベント名で表記が変わる）
- [ ] **型名・インターフェース名**（PascalCase: `QueryRewriteConfig` 等）で grep する
- [ ] **定数名**（SCREAMING_SNAKE_CASE: `ENABLE_QUERY_REWRITE` 等）で grep する
- [ ] i18n の**キー**（`settings.queryRewrite.label` 等）で grep する

典型的な所在: `src/` 全般、schema・型定義、i18n キー、環境変数・設定ファイル、ドキュメント。

```bash
# 例: 撤去対象 "queryRewrite" の識別子走査（表記ゆれを機械的に列挙してから grep）
grep -rn -i -E 'queryRewrite|query_rewrite|query-rewrite|QUERY_REWRITE' \
  --exclude-dir=node_modules --exclude-dir=.git .
```

## 系統 2: 表示文言

識別子を消しても、**画面に出ていた文字列**でテストが結合している。

- [ ] i18n リソースの**値を開き**、撤去した UI のラベル・説明文の実文字列を確認する（キーではなく値）
- [ ] その実文字列で **ja / en 双方**を grep する（`getByRole("switch", { name: "クエリリライト" })` のように、テストはロケールの実文字列で要素を掴む）
- [ ] aria-label・placeholder・エラーメッセージ等、i18n を経由しない直書き文言も探す

典型的な所在: **E2E テスト**、**アクセシビリティ（a11y）テスト**、スナップショット、ヘルプ・ドキュメント。

```bash
# 例: 撤去した UI ラベルの実文字列（ja/en）でテストを走査
grep -rn -e 'クエリリライト' -e 'Query Rewrite' e2e/ tests/ src/
```

## 系統 3: 構造セレクタ・モック応答

3 系統のうち**最も見つけにくい**。「何を消したか」ではなく **「消した挙動を誰が観測しているか」** で探す必要があり、grep 語が撤去対象の名前と一致しないため。

- [ ] **CSS クラス**（`.fc-faq` 等）: 撤去した要素に付いていたクラス名で grep する
- [ ] **`getByRole` / `getByTestId` / `data-testid`**: 撤去した要素を掴んでいたセレクタで grep する
- [ ] **モック応答**: 撤去した挙動を**発火させる入力値・レスポンス**（`{questions: []}` のようなモックデータ、fixture、API スタブ）で grep する。撤去対象の名前を含まないデータが撤去対象の分岐を観測していることがある
- [ ] **スナップショット**: 撤去した要素を含むスナップショットファイルを更新・削除する

典型的な所在: **E2E テスト**、**スナップショット**、fixture・モックデータ、Storybook。

**E2E / スナップショット / a11y テストのディレクトリは名指しで走査対象に含める**（例: `e2e/`、`__snapshots__/`、`tests/a11y/`）。系統 1・2 の grep が src だけを見て緑になっても、これらのディレクトリに観測者が残る。

```bash
# 例: 撤去した要素の構造セレクタとモック値でテスト資産を走査
# （-r が src/ 配下の __snapshots__/ も再帰で拾う。`**` glob は bash 3.2 で
#  再帰展開されないため使わない。エラーを 2>/dev/null や || true で隠さない —
#  パス不正で未走査のまま「残存参照なし」と誤読する事故を防ぐ）
grep -rn -e 'fc-faq' -e 'data-testid="faq' -e 'questions: \[\]' e2e/ tests/ src/
```

## 警告: E2E がデプロイ済み成果物を指す構成

E2E が**デプロイ済み成果物**（埋め込みウィジェット・公開 SDK・CDN 配信バンドル等）を読み込む構成では、**撤去 PR の破壊はブランチ上の E2E では検出できない**。ブランチの E2E は旧成果物（staging / production の URL）に対して走るため緑のままで、破壊は**デプロイ後に発現**する。

- [ ] E2E の対象 URL・バンドル参照（例: `WIDGET_BUNDLE_URL` のような環境変数）が**ローカルビルドかデプロイ済みか**を確認する
- [ ] デプロイ済みを指す場合、その旨と「デプロイ後に E2E を再実行して検証する」計画を PR 本文へ明記する

## 完了条件

- [ ] 3 系統すべてを実施した（省略した系統がない）
- [ ] 系統ごとに使った grep 語（表記ゆれ・実文字列・セレクタ・モック値）を PR 本文へ記載した
- [ ] E2E / スナップショット / a11y テストのディレクトリを名指しで走査した
- [ ] E2E がデプロイ済み成果物を指す場合、ブランチで検出できない旨を PR に明記した
- [ ] 残存参照が 0 件であること、または残す参照の理由を PR 本文へ記載した

## 重要ルール

- 「識別子で grep して 0 件」を「残存参照なし」と読み替えないこと（それは 3 系統のうち 1 系統の結果にすぎない）
- grep 語は撤去対象の名前から機械的に導出できるとは限らない。系統 3 は**撤去した挙動の観測者**（テスト・モック・スナップショット）側から逆引きすること
- 走査で見つかったスコープ外の問題は、その場で直さず `/out-of-scope-issue` でルーティングすること
