# 起票フロー（/retrospective）

`/retrospective` の SKILL.md から、提案を 1 件以上出すとき（閾値到達の昇格・`Kind: keep` の定着・特急レーン・台帳へ書き込めないリポジトリでの提案）だけ読む。提案の閾値の正本は SKILL.md 側、提案の書式（出力形式）は本ファイル末尾にある。

## 起票フロー

### 起票前の既存確認（必須）

提案を提示する**前**に、各提案について次を確認する。同じ手戻りは繰り返し観測されるのが自然で、この確認なしの起票は既存知見・既存 Issue の重複を構造的に生む（実測: 別プロジェクト 2 セッションで、起票した提案の過半が既存知見・既存 Issue の重複、または起票先誤りだった）。確認はすべて read-only なので実行ポリシーには反しない。**確認そのものを実行できなかった場合**（認証エラー・rate limit・知見ストアの配置を特定できない等）は「重複なし」と扱わない — 失敗した事実と重複の可能性が残ることを `既存確認:` へ書いたうえで提示する。

1. **起票先の確定（SSOT 確認）**: 改善対象がスキル・hook・スクリプトなどツール群そのものである場合、その開発元（SSOT）リポジトリで作業しているなら起票先は SSOT にし、配布用の同期ミラーへは起票しない。**これは開発元へ到達できる場合の規則**であり、SSOT が非公開などで到達できない利用者は、手元の配布元リポジトリの Issue へ起票してよい（受け取ったメンテナが SSOT へ transfer する）。**手順 3 の既存 Issue 検索**は、ここで確定した起票先 repo に対して行う（後の手順で起票先を変えた場合は手順 3 をやり直す — ミラー側だけ検索して「重複なし」と判定する誤りを防ぐ）。一方、手順 2 の知見ストアは**手戻りを実測した導入先 repo**（いま作業しているプロジェクト）が対象で、起票先とは別の repo になりうる

   **起票先 repo の解決（手順 1 の具体手順）**:
   - plugin への提案は、ホストのインストール情報から対象 plugin を供給する marketplace checkout の実在パスを確認し、`git -C "<marketplace checkout>" remote get-url origin` で配布元を読む。固定の cache path を推測しない。checkout が無い配布形態では、ホストの登録情報と plugin の repository メタデータを使う。
   - **作業対象リポジトリの owner から類推しない**。remote が HTTPS / SSH のどちらでも、取得した URL の owner/repo を候補として使う。
   - **配布元と SSOT を区別する**: marketplace の remote だけでは開発元とは確定しない。候補 repo の README・AGENTS.md・配布/同期手順と plugin のメタデータで、開発元と配布ミラーの関係を確認する。開発元の明示があればその repo を採る。
   - `gh repo view "<候補 owner/repo>" --json nameWithOwner` で存在・到達性と正規の owner/repo を確認する。起票先の根拠（remote またはメタデータと開発元の記載）も `既存確認:` へ残す。

   | 起票内容 | 起票先 |
   | --- | --- |
   | ツール群の実装・スキル文言・配布物への変更要求 | 到達可能な SSOT。配布ミラーへ新規起票しない |
   | 公開側に既にある外部利用者の不具合報告への応答 | その公開 Issue へ返信。実装修正の管理先は SSOT |
   | 作業対象プロジェクト固有の課題 | そのプロジェクトで実測した remote の repo |

   - **解決不能なら起票しない**: 起票先の owner/repo の実在・正規名を確認できなければ推測で確定せず、`既存確認:` に未確定の理由を書いて確認事項として提示する。認証・通信障害を repo 不在とみなさない。
   - **公開配布物だけの利用者**: 開発元が非公開・非開示で SSOT 関係を確認できない場合も、存在確認済みの配布元へ起票する fallback は維持する。配布元を SSOT と断定せず、`既存確認:` に「SSOT は確認不能・配布元へ受け渡し」と明記する。起票の実行は「承認と起票」の規定に従う。

   **SSOT の現況照合（手順 1 の続き）**: スキル・hook・スクリプト等への改善提案は、既存 Issue の検索とは別に、SSOT の既定ブランチで当該記述を照合する。手元の配布済みプラグインや作業ブランチの本文を最新版とみなさない。
   - 既定ブランチは `gh repo view "<SSOT owner/repo>" --json defaultBranchRef --jq '.defaultBranchRef.name'` で取得する。提案が指摘するファイル・箇所と期待する振る舞いを対応付けて読む。
   - **clone がある場合**: remote URL が SSOT と一致することを確認し、`git -C "<SSOT clone>" fetch "<確認済み remote>" "refs/heads/<既定ブランチ>"` が成功した直後の `FETCH_HEAD` の SHA を記録する。`git -C "<SSOT clone>" show "<取得した SHA>:<対象 path>"` で読む。fetch 失敗時に古い remote-tracking ref へ戻らない。
   - **clone が無い場合**: `gh api "repos/<SSOT owner/repo>/git/ref/heads/<既定ブランチ>" --jq '.object.sha'` で SHA を取得し、`gh api -H "Accept: application/vnd.github.raw+json" "repos/<SSOT owner/repo>/contents/<対象 path>?ref=<取得した SHA>"` で本文を読む（path は URL エンコードする）。web で同じ SHA のファイルを読んでもよい。
   - **すべて修正済み**: 新規起票は行わず、「SSOT では対応済み（該当コミット/該当箇所）」として提案を取り下げる。配布版の更新待ちと未実装を混同しない。
   - **取り下げても台帳は書き戻す**: 取り下げた対象が閾値到達エントリなら、`Status` を `mitigated`・`Issue` を対策の所在（ここでは SSOT の該当箇所）へ更新する（値域と復帰条件の正本は [promotion.md](promotion.md)）。取り下げは「承認と起票」手順 5 を通らないため、ここで書き戻さないとエントリが `active` のまま残り、次の再発で同じ見送りを再演する。
   - **一部だけ修正済み**: 未修正の残余だけに絞った提案を提示し、修正済みの部分は提案本文から除く。以降の既存確認も残余を対象に行う。
   - **照合できない場合**: 認証・通信・取得失敗や対象 path 不明を「照合不能」と記録し、「修正済みでない」と扱わない。SSOT へ到達できず配布元へ起票する場合もこの区別を保つ。
   - **結果の記録**: `既存確認:` 行へ SSOT の repo・既定ブランチ・確認した SHA/path と、対応済み・一部対応済み・未対応・照合不能の判定を書く。取り下げた提案もこの行と理由だけを報告する。台帳の観測履歴自体はこの照合で取り下げない（記録は実測の事実、取り下げるのは提案）。

2. **知見ストアの grep**: 対象は導入先 repo（手順 1 参照）。まず知見ストアの**実配置を確定する** — 既定は索引 `docs/08-knowledge/PLAYBOOK.md` とエントリ `docs/08-knowledge/playbook/**` だが、配置はプロジェクト規約で異なる（実測: 導入先の 1 つは `docs/playbooks/playbook/**` に置いている）。既定パスが無ければ `PLAYBOOK` / `playbook` を repo 内で検索して実配置を突き止める。**既定パスの不在だけを根拠に「ACE 未導入」と結論しない** — この誤判定は手順 2 を丸ごと飛ばすため、重複の見落としに直結する。確定した索引とエントリを提案のキーワードで grep し、ヒットしたエントリごとに分岐する:
   - **エントリが恒久対策の Issue を指している**: その Issue を手順 3 で確認し、新規起票の代わりに **Issue への再発コメント追記**を提案として出す
   - **恒久対策の Issue を指していて新規起票を見送った**場合、その対象が閾値到達エントリなら `Status` を `mitigated`・`Issue` をその恒久対策の所在へ書き戻す（正本は [promotion.md](promotion.md)）。ここも「承認と起票」手順 5 を通らない経路である
   - **指していない**: 知見として既知でも、対策が Issue として管理されていない状態である。**既存エントリを参照した新規起票**を行い（提案に参照先のエントリ ID を書く）、あわせて既存エントリのカウンター更新も提案する。「記録済み」を起票しない理由にしない

   検索しても知見ストアが見つからない repo でだけ本手順をスキップして手順 3 へ進む（手順 1・4 は ACE の有無にかかわらず常に行う）
3. **既存 Issue の確認**: まず起票先 repo の open な `bundle`（着手単位。子 Issue を全件 1 PR で束ねる Issue）を `gh issue list --repo "<owner>/<repo>" --state open --label bundle --limit 200` で列挙し、**改善対象が導入先の CLAUDE.md / docs の規律（散文の追記）なら、表題に「規律」を含む bundle へのコメント追記を既定にする**（単独の docs Issue を立てない。`bundle` ラベルが実在しない repo ではこの列挙を飛ばす）。次に既存 Issue を state を絞らずに検索する（`gh issue list --repo "<owner>/<repo>" --search "<キーワード>" --state all --limit 200`。`--limit` は省略しない — 既定では取得が 30 件で打ち切られ、その先にある重複を「無い」と誤判定する）。重複する Issue が既にあれば新規起票せず、ヒットした Issue の state で分岐する:
   - **open**: **既存 Issue へのコメント追記**（再発情報の集約先として）を提案する
   - **closed**: closed へのコメント単独では作業として追跡されないため、未対応のまま閉じられていたなら **reopen** を、修正後の再発なら **closed Issue を参照した regression Issue の新規起票**を提案する（どちらなのかを提案に明示する）

   ヒットした open Issue は本文を**全文**読み（先頭だけで切らない）、重複でなくても提案がその Issue の定める方針・制約に矛盾しないことを確認する — 矛盾する提案はそのまま出さず、方針側の変更提案であることを明示するか取り下げる
4. 何を grep / 検索してどう判断したかを、各提案の `既存確認:` 行（SKILL.md の出力形式）に 1 行で書く。この行を書けない提案は提示しない

### 承認と起票

1. SKILL.md の出力形式で提案を提示する
2. **起票モードを判定する** — 既定は**承認を待たずに起票する**（自動起票）。承認待ち式は保険 `RETROSPECTIVE_FILING=ask` でだけ有効になる。判定は次の順で行い、env を実測せずに「未設定だろう」と決めない（`RETROSPECTIVE_MODE` の判定と違い、本スキルの明示呼び出しは env を無視する理由にならない — 起票は外向き書き込みなので、明示呼び出しでも ask 設定は尊重する）:
   1. 利用者がそのセッションで起票の扱いを直接指示している（「起票して」「起票は確認してから」等）→ その指示に従う
   2. hook から発火した → 注入文に `RETROSPECTIVE_FILING=ask` があれば ask、無ければ既定
   3. 上記のどちらにも該当しない（hook 外のチェーンからの暗黙実行、hook が動かない環境や `off` 設定下での明示呼び出しを含む）→ 環境変数を実測する（エージェントは env を自動では観測できないため、この確認を省略しない）:

   ```bash
   printenv RETROSPECTIVE_FILING
   ```

   出力が `ask`（大文字小文字と空白を無視）なら ask モード、未設定（空）・それ以外の値なら既定モード。

   - **既定モード（自動起票）**: 「起票前の既存確認」を完了し起票先 repo が確定した提案について、承認を待たずに手順 3〜5 を同じ応答内で実行し、**実施した事実と発行番号を振り返り結果で報告する**（SKILL.md の出力形式の `起票:` 行）。ノイズ抑制は台帳の閾値（Count 3 / 特急レーン）と既存確認が担っており、承認ゲートはそれらと重複した確認になるため既定から外している。起票は close で戻せる可逆操作として扱う
   - **既定モードでも起票せず提示に留めるもの**（承認の問題ではなく、構造的に起票先または内容を確定できないもの）: 起票先の owner/repo を確定できない・「起票前の既存確認」を実行できなかった（認証エラー・rate limit 等）・ヒットした open Issue の方針と矛盾する（方針側の変更提案として提示する）・個人環境（`~/.claude` 等）への提案。いずれも `既存確認:` 欄に理由を書き、`起票:` 行を「見送り（理由）」にする
   - **ask モード（`RETROSPECTIVE_FILING=ask`）**: 提案を提示して**ユーザー承認を待つ**（承認なしに起票しない）。ただし、利用者がそのセッションで当該作業を含む**包括的な実行指示**（「最後までやって」「起票まで進めて」等。「マージまで進めて」のようにチェーン末尾の振り返りより前で終わる指示は含まない）を直接出している場合は、その範囲内の観測 Issue の起票・既存 Issue への再発コメント追記・台帳エントリの Count 更新（Count 更新はもともと承認不要の定型記録）について改めて確認を取らずに実施し、実施した事実と発行番号を振り返り結果で報告する（利用者の直接指示は skill に優先する）
   - ask モードの包括指示例外は特急レーン（データ破壊・広範な作業停止・セキュリティの重大起票）には及ばない — ask を選んだ利用者には重大さの判断そのものを見せる価値があるため、包括指示があっても提案を提示してから実施する
3. 起票対象（既定モードで既存確認を完了した提案、または ask モードで承認された提案）のうち**新規起票**のもの: 起票先 repo へ Issue を作成する。ff-dev-toolkit 導入 repo では `/create-issue` を**既定**とする（種別・優先度ラベルの実在確認付き付与まで行われる）。素の `gh issue create` は `/create-issue` が使えない環境向けの fallback で（`docs/` のコア文書が無い、AC を書く材料が揃わない場合を含む）、**そのままではラベルが付かない**。ラベル付与手順の正本は `/create-issue`（`skills/create-issue/SKILL.md`「ラベルの決定」）であり、ここでは逐語複製せずその verify-then-skip をそのまま用いる: `gh label list --repo "<owner>/<repo>" --limit 200 --json name --jq '.[].name'` で実在するラベル名を取得し、**存在するものだけ** `--label` へ渡し、省略した系統は「不在」と「照会失敗」を書き分けて報告する。

```bash
# 上で実在を確認できた系統だけを --label に残す（存在しないラベル名を渡すと
# 起票自体が失敗する）。確認できなかった系統は、その --label を丸ごと削って実行する
gh issue create --repo "<owner>/<repo>" --assignee @me \
  --label "<実在確認済みの type ラベル>" --label "<実在確認済みの priority ラベル>" \
  --title "<提案タイトル>" \
  --body "<実測の経緯 + 提案内容 + 期待効果>"
```

4. 起票対象のうち**既存への追記へ切り替えた**もの: 新規起票はしない。既存 Issue へのコメント追記は `gh issue comment "<Issue番号>" --repo "<owner>/<repo>" --body "<再発の実測・経緯 + 元提案の内容>"` で行う。既存 ACE エントリのカウンター更新は本スキルでは行わず、ACE 側の手順（`/ace-curate`、または導入 repo の Playbook 記述ガイドライン）へ回す
5. 昇格起票した提案は、起票後に対応する台帳エントリの `Status` を `promoted`、`Issue` を発行番号へ更新する（定型書き込み）。対策が既に別の場所にあるため起票そのものを見送った閾値到達エントリは、代わりに `Status` を `mitigated`、`Issue` を対策の所在へ更新する（同じく定型書き込み。値域と復帰条件の正本は [promotion.md](promotion.md)）
6. 発行された Issue 番号を報告して終了する。既存への追記へ切り替えた提案は、新規番号の代わりに追記先（コメントした Issue 番号・更新を依頼したエントリ ID）を報告する

## 出力形式

提案は次の書式で提示する（SKILL.md「出力形式（提案がある場合）」が指す正本）:

```text
## セッション振り返り

1. [提案タイトル]
   - 実測: [このセッションで実際に起きたこと（何にどれだけ手戻り/時間を要したか）]
   - 提案: [変更内容（スキル文言追加・ツール修正・ゲート化など）]
   - 既存確認: [何を grep / 検索して重複・方針矛盾なしと判断したか。重複時は追記先への切替を明記]
   - 起票先: [owner/repo]
   - 付与予定ラベル: [type / priority（付与しない場合は「なし」と理由）]
   - 期待効果: [何が速く/正確になるか]

2. ...（最大 3 件）

起票: [owner/repo#N（新規）/ owner/repo#M へ再発コメント追記 / 見送り（理由）— 提案ごとに 1 行]
```

`起票:` 行は既定モード（`RETROSPECTIVE_FILING` 未設定）で、同じ応答内で実行した起票・追記の結果を書く（結果を書かずに提案だけで終えない）。`RETROSPECTIVE_FILING=ask` のときは `起票:` 行の代わりに `承認いただければ起票します。` で終え、承認後に結果を報告する（ask モードでも包括指示の例外で同じ応答内に起票した場合は、既定と同じく `起票:` 行で結果を書く）。`既存確認:` 欄は「起票前の既存確認」を実施してから記入する（実施していない提案は提示しない）。昇格提案では、根拠となる台帳エントリの OBS ID と Count を `実測:` 欄へ併記する。
