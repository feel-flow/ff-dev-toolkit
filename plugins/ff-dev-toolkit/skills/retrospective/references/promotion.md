# 昇格・見送り・再発の扱い（/retrospective）

`/retrospective` の観察チェックリストと「昇格閾値と特急レーン」から、次のときに読む: 発行済み Issue の対策完了を照合するとき・閾値到達エントリの昇格先を決めるとき・`promoted` / `mitigated` のエントリへ再発を記録するとき・閾値に到達したが昇格を見送るとき。判定対象（`active` のみ）と閾値（累計 3 回）の正本は SKILL.md 側にある。

## 起票先

- **昇格の起票先は改善対象で分岐する**（解決手順の正本は [filing.md](filing.md)「起票前の既存確認」手順 1）: 改善対象がスキル・hook・スクリプトなどツール群そのものなら到達可能な SSOT（到達できなければ配布元）、作業中プロジェクト固有のプロセス・手順なら**作業中リポジトリ自身**の Issue。台帳がどのリポジトリにあるかではなく、修正が入る場所で決める

## 発行済み Issue の対策完了と旧台帳の移行

`promoted` は対策 Issue に追跡を委ねている状態で、対策完了の確認済みを意味しない。`mitigated` との差は **対策の反映を確認したか** であり、Issue を発行したかではない。

1. **完了照合は既存の振り返りで行う**。そのセッションで対応を終えた Issue に紐づく観測を照合する。旧台帳の移行・棚卸しでは `promoted` 全件の `Issue` 列を列挙し、リポジトリ修飾の番号ごとに state・完了理由・本文・コメントを取得する。`--promoted-open` は closed を除くため、完了照合の母集団には使わない。毎回の振り返りで全履歴の移行を繰り返す必要はない。
2. **closed だけでは `mitigated` にしない**。完了報告の指す対策を現行の正本の SHA/path・該当節または実装と突き合わせる。未対応の close、重複・見送りによる close、照会失敗、対策の消失、未解消の再発や open の後続対策がある場合は移行を保留する。重複先で完了したものは重複先まで同じ照合を行う。原因工程の撤去など別の対策で前提が解消したものは、その決定と現行実体を照合し、元 Issue の AC 達成とは区別して記録する。複数 Issue が並ぶ観測は、古い closed 1 件だけで行全体を完了にしない。
3. **対策反映を確認できた `promoted` を `mitigated` へ更新する**。`Issue` 列には **元 Issue 番号を残し、対策の所在を併記する**（`owner/repo#N / skill:<スキル名>` または `owner/repo#N / doc:<path>#<アンカー>`）。実装のみの対策は、その実装を指す運用文書・スキルと実装 path を確認メモへ記録する。別リポジトリの参照はそのリポジトリ名を添えて所属を明示する。
4. **状態移行では `Count`・`First`・`Last` と既存の観測履歴を変えない**。移行日・元 Issue・確認した SHA/path・判断根拠を「状態移行（再発ではない）」として追記する。保留にも確認日と理由を残し、再照合時は新しい証拠があるものだけ再判定する。参照不能を対策済み・未対策のどちらにも決めつけない。移行結果には候補全件の移行済み／保留と理由を含め、件数を過去の棚卸し時点へ固定しない。

移行対象は作業中リポジトリの台帳である。他リポジトリの同じ OBS ID を混同せず、その台帳の書き換えは依頼範囲に含まれるときだけ行う。状態移行も台帳への定型記録であり、書き込み・鮮度確認は [ledger.md](ledger.md) に従う。

## 元 Issue がある観測の再発

- `promoted` 済みのエントリが再発したら、`Count` +1 と観測メモに加えて、リンク先 Issue の state に応じた提案を出す（open → 再発の実測をコメント追記 / closed → reopen または regression 起票。分岐の正本は [filing.md](filing.md)「起票前の既存確認」手順 3）— 再発の実測を台帳の中だけに眠らせない
- **元 Issue がある `mitigated` も同じ再発分岐を使い、`Issue` 列を `なし` にしない**。open なら追記、未対応のまま closed なら reopen、修正後の再発なら元 Issue を参照した regression を扱う。再開・既存 open への集約・regression 起票が実際に成立したら `promoted` とし、現行の対応先と元 Issue・対策所在を併記する。成立前や照会不能では状態・参照を保持し、未解消再発／追跡先未確定と理由を観測メモへ書く（状態名だけで対策有効と読まない）。提案・外部書き込みの扱いは [filing.md](filing.md) に従う。
- **closed 済み対策の再発時は、前の対策と同じ型を再提案しない** — リンク先 Issue が closed なのに再発したなら、その対策は効かなかったという実測である。regression 起票の提案では、前の対策と同じ型（規定文言の追加・参照経路の追加・needle 追加・名簿修正といった「到達点を増やす」型）を候補にせず、**構造を変える案**（判定をゲート側へ移す・経路自体を減らす・その工程を廃止する）だけを候補にする。構造案が無ければ「同型対策は不採用・構造案なし」を観測メモへ 1 行書き、提案なしで終える。同型かどうかの判定は推論に委ねる（型の列挙は例示であり、閉じない）。根拠は OBS-036（対策 4 世代）・OBS-013（対策 3 世代）で、いずれも到達点を増やす方向の対策が上限に達していた

## `mitigated`（対策済みを状態として書き戻す）

- **`mitigated`（対策済み）** — 既存対策の反映を確認して昇格を見送ったエントリ、または発行済み Issue の対策完了を上の手順で確認したエントリ。見送り・完了の判断を状態として台帳へ書き戻し、観測は続ける。Issue が存在するだけでは対策反映の確認にならない
- `mitigated` の `Issue` 列には**対策の所在**を接頭辞付きで書く: 発行済み Issue なら `owner/repo#N`、スキルなら `skill:<スキル名>`、文書なら `doc:<path>#<アンカー>`（複数あれば ` / ` で並べる）
- `mitigated` のエントリが再発したら `Count` +1 と観測メモの追記は行うが、閾値だけを根拠に **昇格提案は再演しない**。元 Issue がある場合は上の再発分岐を使う
- **`mitigated` の再発を記録するときは `Issue` 列の参照先を確認する**（完了照合時の証拠を固定せず、再発時点の参照先を確認する）: Issue 参照は `gh issue view <N> --repo <owner/repo> --json state`、`skill:` / `doc:` 参照は該当スキル節・path の実在を grep で確かめる。確認できなかった場合は「対策あり」と扱わず、確認不能である旨を観測メモへ残す
- **`active` への復帰条件** — 元 Issue がない見送り分だけが対象。次のどちらかに当たったら `Status` を `active` へ戻し、閾値判定の対象へ復帰させる。判断は振り返り実行時の定型書き込みで、根拠を観測メモに 1 行残す
  - (a) **対策が失われた**: 参照先のスキル節・文書が削除された
  - (b) **対策が効いていない**: 再発の観測メモが「対策を適用したのに再発した」と読める
  - 戻すときは **`Issue` 列も `なし` へ戻す** — `skill:` / `doc:` / Issue 参照を残したままだと昇格条件の未リンク判定を満たさず、`active` へ戻しても提案が出ない。旧所在は復帰の根拠として観測メモの 1 行に書き残す
- `archived` は休眠、`mitigated` は対策反映を確認済み（再発の有無は問わない）。現在も対策が有効かは参照先と最新の観測メモで判断する。
