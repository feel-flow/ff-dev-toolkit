# ワークフロー運用原則

> **Parent**: [DEPLOYMENT.md](../DEPLOYMENT.md) | **Related**: [git-workflow.md](./git-workflow.md)

## 概要

AI駆動Git Workflowを効率的に運用するための基本原則を定義します。これらの原則はワークフロー全体に適用され、不要な中断を排除し、スコープの肥大化を防ぎます。

---

## 3つの運用原則

### 原則1: ノンストップフロー（フルオート）

**ルール**: Issue作成から振り返りまで、不要な確認を挟まず一気通貫で進める（push / Draft PR / ready / merge / cleanup / ACE / `/retrospective` の実施を含む）

```
Issue作成 → ブランチ作成 → 実装 → テスト → セルフレビュー
  → Commit/push → Draft PR → Toolkit+Codex レビュー → 1 fix commit
  → gh pr ready → /close-issue（AC照合ゲート） → gh pr merge --squash
  → /merge-cleanup → ACE → /retrospective（セッション振り返り）
                    ↑ この一連の流れを中断しない（フルオート） ↑
```

> `/retrospective` はノンストップの範囲が**実施（振り返り + 提案の提示）まで**。改善提案の Issue 起票はチェーン外で、ユーザー承認を待ってから行う（承認ゲートは起票側にある。下の「止めてよい例外」の追加ではなく、フローがここで自然に終端する）。
> 対応ホストでは Stop hook が応答終了前に自動継続する。`RETROSPECTIVE_MODE=ask` で実施前確認、`off` で自動発火を無効にできる。

> **スキル未解決時のフォールバック**: チェーンのスキルが `Unknown skill` で解決できない場合、まず名前を疑う — セッションの利用可能スキル一覧をキーワードで検索して実名を確認し、プレフィックス付き（`<プラグイン名>:<スキル名>`）と無しの両方を試す（両者は別名として共存しうる）。`ListSkills` が返すのは claude.ai 側の別レジストリであり、その空振りを不在の根拠にしない。一覧にも無い場合（インストール済みプラグインが該当スキルの追加より古い）は、プラグインを更新するか、インストール済みプラグインの `skills/<スキル名>/SKILL.md` を直接 Read して手順に従う。それでも解決しない場合は、リポジトリ内の実体（`plugins/<プラグイン名>/skills/<スキル名>/SKILL.md`）とインストール済みプラグインディレクトリの中身を突き合わせる — プラグインが複数ディレクトリへ分割インストールされ、一部スキルが当該セッションのレジストリに載っていないことがある。その場合はリポジトリ側の SKILL.md を読んで手順に従う（スキルが存在しないと結論しない）。

**やること**:

- 各ステップを順序通りに連続実行する（外向き操作も確認なし）
- セルフレビューの指摘は即座に修正して 1 fix commit に束ねる。fix commit で実装が Issue の AC の前提を超えた／変えた場合は、その場で Issue 本文の該当 AC も更新する（変わった理由を 1 行添える。スコープ外発見を別 Issue の AC へ追記する場合は原則2 に従う）
- レビュー対応ポリシーに従い、Critical/Warning は確認不要で即対応
- 進捗は TodoWrite と短い完了報告で可視化する（承認待ちにはしない）

**やらないこと**:

- 途中で不要な「これでいいですか？」「push していい？」「merge していい？」確認を挟む
- 実装完了後にPR作成・マージを後回しにする
- セルフレビュー結果を報告して承認を待つ
- 「外向き操作だから」という理由だけでフローを止める

**止めてよい例外（限定列挙）**:

1. **破壊的・不可逆操作** — force-push、`git reset --hard`、本番や共有インフラへの破壊的変更
2. **実装続行不能な致命的仕様不明** — 確認しないと物理的に進められない、または誤実装で大幅手戻り・セキュリティ/データ整合性事故になる
3. **安全上の実害** — 同一ブランチでの並行セッション衝突、他人の未コミット作業の上書きなど

### 原則2: スコープ外発見の三分岐

**ルール**: 作業中にスコープ外の改善点・バグを見つけた場合、**YAGNI → インライン修正 → Issue 化** の順で判定する。一律に Issue 化せず、一律に「ついで対応」もしない。

| 判定 | 条件 | 対応 |
| ---- | ---- | ---- |
| YAGNI | 現在の再現例・利用者影響・運用上の痛みがなく、検証可能な受け入れ条件を書けない | 対応せず、Issue も作らない。理由だけ報告する |
| インライン修正 | 必要性があり、仕様判断・別モジュール波及・独立検証・実装 10 行超（テスト・fixture は数えない）のいずれにも明確に該当しない（近傍の設定ファイルの小変更も含む） | 現 PR の fix commit に束ねる |
| Issue 化 | 必要性があり、仕様判断・別モジュール波及・独立した受け入れ条件や検証・実装 10 行超（テスト・fixture は数えない）のいずれか 1 つに明確に該当する | 類似 Issue を検索し、統合できればコメント、独立するなら関連 Issue を作成する。同一 PR からの複数発見は既定で 1 Issue に束ねる。本文 AC の追記は明示許可と競合確認がある場合だけ行う |

判定の既定方向は軽量側（「Issue 化を示せるまでインライン」）。ただし迷いの扱いは軸ごとに違う — 仕様判断・別モジュール波及の 2 軸は不確かでも Issue 化へ倒し（安全側）、規模・局所性・検証の重さの迷いはインラインへ倒す。

現在の diff が導入・悪化させた回帰、現 Issue の受け入れ条件、既存契約、必須品質ゲート、Critical / Warning の解消はスコープ外ではない。後続 Issue へ送らず、マージ前に現 PR で解消する。

**やること**:

- 最初に現在の根拠と受け入れ条件を確認し、YAGNI なら backlog に積まない
- 必要かつ軽微な発見は、理由を 1 行報告して現 PR で修正
- 必要かつ非軽微な発見は、先に類似 Issue を検索する
- 同じ完了条件へ軽微に吸収できる場合は、既定は既存 Issue への発見元コメントだけで集約する。本文 AC は明示許可があり、編集直前に `body` / `updatedAt` の競合がない場合だけ最小追記する
- 完了条件が独立する場合は、発見元と受け入れ条件を添え、既存 Issue と関連付けた新規 Issue として記録
- 現在のタスクに集中し続ける

**やらないこと**:

- 将来の可能性だけで Issue を作る
- 類似 Issue を確認せず重複 Issue を作る
- 用語が似ているだけの Issue へ無理にまとめ、既存の目的や AC を書き換える
- 仕様判断や別モジュール変更を「軽微」として現 PR に混ぜる
- 現 diff の回帰や必須品質ゲートを「別 Issue」として先送りする

**例**:

```bash
# 必要性があり、独立した設計・検証が必要なリファクタリングを発見した場合
expected_repo="OWNER/REPO" # 現在の PR / Issue URL と対象範囲から確定
gh issue create \
  --repo "$expected_repo" \
  --title "refactor: UserService のメソッド分割" \
  --body "## 発見の経緯
Issue #123 の作業中に発見。UserService.createUser() が150行を超えており、
バリデーション・永続化・通知の責務が混在している。

## 提案
- バリデーション、永続化、通知を個別メソッドに分離
- 単体テストの追加

## 優先度
低（機能的には正常に動作中）" \
  --label "refactor"
```

### 原則3: 曖昧仕様の確認タイミング

**ルール**: 要件が不明確な場合はIssue着手前にユーザーに確認する。作業開始後に出てきた疑問は原則2で必要性と変更境界を判定し、現在の作業を止めない

| タイミング                   | 対応                                          |
| ---------------------------- | --------------------------------------------- |
| Issue着手前                  | 曖昧な要件・仕様をユーザーに確認              |
| 作業開始後（非致命的な疑問） | 原則2で YAGNI / インライン / Issue 化を判定する |
| 作業開始後（致命的な不明点） | 例外的に作業を止めてユーザーに確認してよい    |

**致命的な不明点の判断基準**:

- 確認しないと実装が物理的に進められない
- 誤った実装をすると大幅な手戻りが発生する
- セキュリティやデータ整合性に直結する

## タスク管理: TodoWrite

ワークフローの各ステップを TodoWrite で管理し、進捗を可視化します。

### 標準チェックリストテンプレート

ワークフロー開始時に以下のタスクリストを作成：

```
1. [ ] GitHub Issue 作成
2. [ ] feature ブランチ作成
3. [ ] 実装
4. [ ] テスト実行・合格確認
5. [ ] Push + Draft PR 作成
6. [ ] セルフレビュー: PR Review Toolkit
7. [ ] セルフレビュー: Codex CLI クロスモデルレビュー
8. [ ] レビュー指摘修正（1 fix commit）
9. [ ] gh pr ready → /close-issue（AC照合ゲート） → gh pr merge --squash
10. [ ] /merge-cleanup
11. [ ] ACE
12. [ ] /retrospective（セッション振り返り）
```

### 運用ルール

- タスク開始時に `in_progress` に更新
- タスク完了時に即座に `completed` に更新
- **同時に `in_progress` のタスクは1つだけ**
- スコープ外の発見は新規タスクとして追加せず、原則2でルーティング

---

## 原則の適用タイミング

| ワークフローステップ | 適用される原則                                                |
| -------------------- | ------------------------------------------------------------- |
| Issue作成            | 原則3（曖昧仕様の確認）                                       |
| ブランチ作成〜振り返り実施 | 原則1（ノンストップフロー / フルオート。`/retrospective` の起票のみ承認待ち） |
| 実装中の発見         | 原則2（YAGNI / インライン / Issue 化）                        |
| セルフレビュー       | 原則1 + [Review Response Policy](./review-response-policy.md) |
| レビュー対応         | 原則1 + 原則2                                                 |
| push / ready / merge | 原則1（外向きでも確認しない。例外は限定列挙のみ）             |
